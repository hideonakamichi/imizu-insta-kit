# carousel_spec.json スキーマ

バナー投稿（カルーセル）の構成設計書。**司令塔（carousel スキルを動かしているセッション）が、theme-picker の選んだ
記事の節（`source_path`）を読んで設計**し、`banner.py --spec` に渡す。1投稿=1ファイル。
`OUTPUT_DIR/carousel_spec.json` に置く。

## 記事紹介として設計する（2026-09-20〜・最優先）

投稿は**オウンドメディアの記事の紹介**として作る。1行のテーマだけから文言を起こしていた頃は
「興味の出どころを聞く」「対象を一つに絞る」のような、どの本にも書いてある一般論になり、
中身が薄かった。記事には一次資料の名称・日付・区分・手順が書かれているので、それを運ぶ。

1. **設計の前に `source_path` を全文読む。** 読まずに書き始めない
2. **書いてよい事実は、その節の本文にあるものだけ。** 数字・日付・資料名・区分名・手順名を
   記事の外から足さない。自分の知識で補わない（`tone.policy`「実績・数値・事例を創作しない」）
3. **content の各枚に、その節に固有の情報を最低1つ入れる。** 固有の情報とは、資料名・年月日・
   数・区分名・手順名・記事が `**…**` で強調している箇所のこと。
   「どの記事にも当てはまる文言」だけでできた枚を作らない。見分け方:
   その枚の記事名を別の記事名に差し替えても通じてしまうなら、薄い
4. **content は3〜4枚を基本にする**（全体で5〜6枚）。節の中身を2枚に押し込むと一般論に戻る
5. `source_path` の「節の本文」の直前に読み方の注意（対話形式で聞き手の感想は事実ではない、等）が
   書かれていれば、それに従う。対話形式のネタ元でも、話者名は画面に出さない
6. 長い資料名は、ネタ元の本文での呼び方（「〇〇調査」「通知」など）に合わせて縮める。
   正式名称はキャプション側で書く
7. `source_path` 冒頭に「注意（この節を扱うときの縛り）」があれば、その指示に必ず従う。
   注意が求める断り書き（「検討中」「案」「個人の感想」等）は、該当する枚の**画面内の文字**として入れる。
   確定した話と未確定の話を同じ枚に混ぜない
8. 表紙と最終枚は、続きを読める場所があるかどうかで分ける（`brand.yaml` の `content_sources.where_to_read`）:
   - **空でない（公開された続きがある）**: cover の `sub` は `記事「<short_title>」より`（20字以内）、
     summary の `headline` は `続きは解説記事で` を基本形に、`sub` は `「<short_title>」`
   - **空（ネタ元が未公開のメモ・FAQ・下書きなど）**: 存在しない閲覧先へ誘導しない。cover の `sub` は内容の補足、
     summary の `headline` はこの節のまとめ、`sub` は保存して使う場面の一言にする
   - どちらも summary の `cta` は `brand.yaml` の `offer.cta_line`。`offer.enabled: false` なら `cta` は入れない
     （保存の案内は `sub` で言う）
   - `source_path` に「全体の前提（ネタ元の導入部）」があれば必ず読む。そこに書かれた限定はこの節にもかかる
9. spec に `source_path` と `article_title` を記録する（evaluator が記事と照合するため）

## スキーマ

```json
{
  "theme": "theme-picker の theme をそのまま（投稿履歴との突合に使う）",
  "slug": "テーマスラッグ（output/ディレクトリ名と揃える）",
  "source_path": "content/articles/<記事スラッグ>/<節ID>.md（theme-picker の出力そのまま）",
  "article_title": "記事タイトル（theme-picker の出力そのまま）",
  "palette": {
    "bg": "#FAF7F2",
    "text": "#1F2A44",
    "accent": "#5B8DB8"
  },
  "slides": [
    {"role": "cover",   "headline": "机の上に置く物は 3つに絞る", "sub": "記事「机まわりの整え方」より"},
    {"role": "content", "headline": "常に置くのは3つだけ", "points": ["パソコン", "飲み物", "メモ"]},
    {"role": "content", "headline": "目的は見た目ではない", "points": ["目に入る情報を減らす", "物があると注意が引かれる"]},
    {"role": "content", "headline": "最初の1週間の記録", "points": ["出たままの物を毎日メモ", "3日続いた物は棚に定位置"]},
    {"role": "summary", "headline": "続きは解説記事で", "sub": "「机まわりの整え方」", "cta": "続きはプロフィールのリンクから"}
  ]
}
```

上の `slides` はあくまで**構造を示すサンプル**。実際の文言は `source_path` の節の本文と
`config/brand.yaml` の読者・トーンから設計する。

## 構造ルール（banner.pyが検証する）

- `slides` は **3〜6枚**。先頭は必ず `role: "cover"`、末尾は必ず `role: "summary"`、
  中間は `role: "content"`（1〜4枚）
- `palette` は **具体的なhex値3色**。`config/brand.yaml` の `design.palette` の値を
  そのまま書き写す（bg=明るく落ち着いた背景 / text=高コントラスト文字色 /
  accent=落ち着いたアクセント1色）。全スライドが同じ3色で描かれ、
  スライド間のスタイル一貫性を担保する。赤系・ネオン系の煽り色は使わない
- `cta` は **summaryスライドのみ**指定可。1行の控えめな案内文（後述）

## 文字量上限（1枚1メッセージと余白を守る — 厳守）

描画は Pillow の決定論的レイアウト（2026-09-11〜）なので誤字は出ないが、文字が増えるほど
縮小されて余白が死に、Minimal の世界観から外れる。1スライドの情報を絞ることがカルーセル化の
目的のひとつ。`headline` は半角スペース1つで改行位置を指定できる（例「机の上の物 3つに絞る」）。

| フィールド | 上限 |
|---|---|
| `headline` | **13文字以内** |
| `sub` | 20文字以内（cover / summary のみ。省略可） |
| `points` | 1項目**15文字以内**・**3項目まで**（content のみ） |
| `cta` | 18文字以内（summary のみ。省略可） |

## role別の設計指針

- **cover（表紙）**: 数字または具体語のフックを断定形で。疑問形・煽り
  （`brand.yaml` の `tone.ng_words` に該当する語）は禁止。subで「何のリストか」を補足。
  スワイプしたくなる「中身の予告」になっていること
- **content（中身）**: **1枚1ポイント**。headlineでポイントを言い切り、pointsで
  2〜3点に絞って補足。詰め込まない（余白 > 情報量）。断定できない情報
  （費用・条件・可否など）は「要確認」の一言を points に含めて断定を避ける
  （`brand.yaml` の `tone.policy`「未確認は未確認と書く」に対応）
- **summary（まとめ）**: 記事への案内＋控えめ誘導（上の「記事紹介として設計する」8）。
  保存の呼びかけはキャプション側に任せる。
  - `cta` は `brand.yaml` の `offer.cta_line` を使う（18文字以内・1行の案内文のみ）。
    ボタン風装飾・URL表記・煽り文言は禁止（evaluatorが不合格にする）
  - `offer.enabled` が false のアカウントでは `cta` を入れない
  - これは `docs/DESIGN.md`「装飾を足さない」方針からの意図的な例外
    （集客目的のため最終枚のみ許可）

## テーマ軸別の推奨構成

`config/brand.yaml` の `strategy_axes` の key に対応する。軸を自分で追加した場合は、
同じ考え方で構成を決める。

| テーマ軸 | 推奨構成 | 構成例 |
|---|---|---|
| how-to（やり方・手順） | cover→手順content×2〜3→summary | 「〇〇の3ステップ」 |
| checklist（確認リスト） | cover→項目content×3〜4→summary | 「〇〇前に見る5項目」 |
| myth-busting（誤解の解消） | cover(通説)→content(実際)×2→summary | 「〇〇＝△△、は誤解」 |
| choice-expansion（選択肢の紹介） | cover→種類content×2〜3→summary | 「〇〇の3タイプ」 |
| numbers（数字ネタ） | cover(数字+意味)→内訳content×2→summary | 「151件の分布」 |
| empathy（共感・気持ち） | cover(状況の言語化)→content×2→summary | 売り込まない回。ctaは省略してよい |

## 設計時のチェック（司令塔自身が spec 作成後に行う）

- [ ] `source_path` を全文読んだうえで書いたか
- [ ] 画面の事実（数字・日付・資料名・区分名）が、すべてその節の本文に見つかるか
- [ ] content の各枚に、その節に固有の情報が最低1つあるか（記事名を差し替えても通じる枚がないか）
- [ ] `content_sources.where_to_read` が空でなければ、cover の sub と summary でどの記事の紹介かが分かるか。
      空なら、記事名や「続きは解説記事で」を出さず、summary がこの節のまとめになっているか
- [ ] `source_path` 冒頭に「注意」があるとき、それが求める断り書きが該当する枚の画面内の文字に入っているか
- [ ] 全フィールドが文字量上限内か
- [ ] cover だけ読んでも「続きを見たい」と思えるか（ただし煽っていないか）
- [ ] content の順序を入れ替えても破綻しない独立性と、通して読んだときの流れが両立しているか
- [ ] 数字を使う場合「その数字が何を意味するか」がスライド内で完結しているか
- [ ] `brand.yaml` の `tone.policy` に反する断定をしていないか
- [ ] `brand.yaml` の `tone.ng_words` の語句が入っていないか
- [ ] `palette` が `brand.yaml` の `design.palette` と一致しているか

## 2026-09-11 の振り返り — 画像生成AIから決定論的描画へ切り替えた理由

### 何が起きたか

金曜9:00の自動実行が、スライド5（summary）を2回再生成しても evaluator を通らず中止した。
手動で7回振り直しても通らず、最終的に不合格版（装飾がエンブレム化した版）を人の判断で投稿した。

| 局面 | 生成 | 合格 |
|---|---|---|
| 自動実行（3周） | 13枚 | 4 |
| 手動（slide5のみ） | 7枚 | 0 |
| **合計** | **20枚** | **4（20%）** |

失敗20件はすべて「文字と線を正確に置けなかった」という同じ種類だった:
書体の混在（明朝混入）4回、勝手な装飾（見切れ・エンブレム・帯・括弧の飾り）6回、
指定にない文字の描画（「」・hexコード・CTAの重複）5回、文字の欠け・崩れ数回。

### 真因

1枚あたりの合格率が20〜30%の生成器に「5枚すべて3回以内で合格」を要求している構造。
合格率30%なら全枚通る確率は約12%、40%でも約30%。**設計上ほぼ毎回止まる。**
9/2の成功（4枚・再生成1回）は再現性のある成功ではなく、当たりを引いた日だった。

つまり原因はプロンプトの書き方でも、禁止文の数でも、cta の有無でもなく、
**画像生成AIに日本語の文字組みをさせていること自体**。カルーセルは無地の背景に
見出し・箇条書き・細い金線・ページ番号を置くだけの構成で、これは画像生成の仕事ではなく
文字組み（レンダリング）の仕事だった。

### やって効かなかったこと（同じ回り道をしないために）

- 装飾の位置・個数・形状・太さをプロンプトで縛る → 縛るたびに別の場所が壊れた
  （見切れ→エンブレム→帯→下線）。相対表現（`hairline`, `about 40%`）は数値として守られない
- 書体をプロンプトで再指定する → 効かない
- 禁止文を削って9/2成功版のプロンプトに戻す → それでも壊れた
- cta を外す → それでも壊れた
- **私（Claude）が立てた仮説2件はどちらも反証された**:
  「禁止文が違反を呼んだ」（hexを直書きに戻しても描画された）、
  「cta が3要素目として原因」（外してもカギ括弧が出た）。
  成功版との差分を取る手法自体は正しいが、差分が「プロンプト」ではなく「生成器の性質」に
  あるときは、プロンプトをいくら揃えても再現しない

### 対策

`banner.py` の生成部を **Pillow の決定論的描画（`render_slides.py`）** に置き換えた。
spec の文字をそのまま置くので、上の失敗は発生原理ごと起きない。同じ spec なら毎回同じ絵。
書体はヒラギノ角ゴシック W8/W6 の2ファイル固定、装飾は座標指定、5枚で1秒未満。
（Lite 版では、Windows でも同じ絵になるよう書体を同梱の Noto Sans JP Black/Bold に替え、Grok 経路は削除した）

evaluator は残す。役割は「文言・発信ポリシー・構成」の判定に絞られる。
**不合格が出たら、同じ spec を描き直しても結果は変わらない。** 原因は必ず spec（文言）か
`render_slides.py` の数値のどちらかにある。

### 今後の判断基準

- 見た目を変えたいときはプロンプトではなく `render_slides.py` の数値を直す
- 「AIに文字を正確に描かせる」設計は、どれだけプロンプトを磨いても宝くじのまま。
  文字が主役の成果物は決定論的に描く。AI生成は写真・イラスト・映像など
  「揺れてよいもの」にだけ使う（リールの映像はこの区分に入る）
