# brand-setup

このテンプレートを、**使う人のアカウント専用**に仕立てる手順。
`config/brand.yaml`（アカウントの人格）と `content/sources/*.md`（投稿の根拠になる文章）を作る。

パイプライン本体（スクリプト・他のスキル）は一切変更しない。
ここで作るファイルだけで、全エージェントの振る舞いが決まる。

## いつ使うか

- テンプレートを受け取った直後（**最初に必ず1回**）
- 発信ジャンル・ターゲット・売りたいものを大きく変えるとき
- 「ネタを増やしたい」だけなら、このスキル全体ではなく手順4だけを実行する

## 手順

### 1. ヒアリングする

以下を利用者に聞く。**一度に全部聞かず、2〜3問ずつに分けて聞く**（まとめて聞くと
答えが雑になり、生成される投稿もぼやける）。

すでにユーザーの発言から分かっている項目は聞き直さず、「〇〇という理解で合っていますか」と
確認する形にする。

**A. 発信の中身**
1. どんなジャンルの情報を発信しますか
2. それを**誰に**届けたいですか（属性ではなく「今どんな状況にいる人か」で答えてもらう）
3. その人は今、何に困っていますか / 何を知りたがっていますか（3つ以上）
4. この発信を通じて、その人にどうなってほしいですか

**B. 売りたいもの**
5. 売りたいコンテンツ・サービス・サイトはありますか（無ければ「無し」でよい）
6. それは何で、読者にとってどう役立ちますか
7. 誘導先はどこですか（プロフィールのリンク先URL等）

**C. トーンと見た目**
8. 避けたい表現・言ってはいけないことはありますか
   （業界特有の規制がある場合は必ず確認する。例: 医療広告ガイドライン、薬機法、
   景表法、金融商品取引法など）
9. アカウントの雰囲気は（落ち着き / 親しみやすさ / 専門性 のどれに寄せるか）
10. 使いたい色のイメージはありますか（無ければこちらで提案する）

**D. アカウント情報**
11. Instagramのハンドル名（@付き）とアカウント名

### 2. `config/brand.yaml` を書く

ヒアリング結果を `config/brand.yaml` の各項目に落とす。ファイル内のコメントに
各項目の意図が書いてあるので、それに従う。**コメントは消さない**（後で利用者自身が
見直すときの手がかりになる）。

書くときの注意:

- `audience.who` は状況で書く。「30代女性」ではなく「〇〇を始めたばかりで、
  何から手をつけるか決めかねている人」のように
- `tone.policy` の既存5項目は**原則そのまま残す**。業種を問わず有効な安全弁であり、
  これがアカウントの信頼を守っている。ヒアリングで出た業界特有のNGは**追加**する
- `tone.ng_words` にはヒアリングで出たNG表現を足す
- `offer.cta_line` は**18文字以内**。超えると最終スライドの文字が縮んで余白が死ぬ
- `design.palette` は3色をhexで決める。`docs/DESIGN.md` の方針
  （明るい背景・高コントラスト文字・落ち着いたアクセント1色）に従い、
  赤系・ネオン系は避ける。利用者に色の希望がなければ、ジャンルの雰囲気に合う3色を
  提案して**確認を取ってから**書く
- `strategy_axes` は既定の6軸で足りることが多い。ジャンル特有の切り口があれば
  差し替える（key は英小文字ハイフン区切り）

### 3. `docs/DESIGN.md` を確認する

`docs/DESIGN.md` は見た目の憲法。Minimal方針のままで問題ないか利用者に確認する。
5節 Tone の1つ目の項目（「上品・落ち着き・信頼感。」の行）だけは、
発信ジャンルに合うトーンの記述に書き換える。

それ以外（3色以内・全テキスト日本語・余白重視・数字は意味とセット）は
**変えないことを推奨**する。この方針が可読性と評価の通りやすさを支えているため。

### 4. ネタ元（`content/sources/*.md`）を用意する

投稿は、利用者自身の文章の1節（`## 見出し` の単位）を根拠にして作られる。1行のテーマだけから
文言を起こすと一般論になり中身が薄くなるため、**根拠になる文章が無いアカウントでは投稿を作れない**。
書式は `content/sources/README.md`。

**A. すでに文章がある場合**（ブログ・note・FAQ・商品説明・講座の台本など）

- Markdown なら `content/sources/` に置いてもらう。`## 見出し` で節に分かれているか、
  1節が200字以上あるかを確認し、足りなければ利用者と相談して直す
- 自サイトの記事HTMLをそのまま使いたい場合は、`brand.yaml` の `content_sources.html` を設定する
  （`enabled: true`・`source_dir`・`base_url`、必要なら `body_class` など）
- 13字を超えるタイトルは、`content_sources.short_titles` に画面用の短い名前を登録する

**B. 文章がまだ無い場合**

利用者にインタビューして、最初の3〜5本を一緒に書く。

- `audience.pains` の1つにつき1本を目安に、「その悩みに、あなたならどう答えますか」と聞く。
  手順・数字・理由・具体例・失敗談を引き出す（ここが投稿の中身になる）
- **利用者が話した内容だけで書く。** こちらの知識で事実・数字・事例を足さない。
  一般論で埋めた文章を根拠にすると、投稿も一般論になり、誤りがあっても誰も気づけない
- 1本につき `## 見出し` を3〜6個、各節200字以上。見出しは `strategy_axes` の `keywords` を
  意識して付けると、テーマ軸が自動で分かれる（例:「手順」「チェック」「誤解」）
- 書いたら**必ず利用者に読んでもらい、事実関係の確認を取る**。確認前のファイルは
  `_` で始まる名前にしておく（ネタにならない）。確認が取れたら `_` を外す

**C. 扱いに縛りがある話題**

手順1のC-8で業界特有の規制や「言ってはいけないこと」が出ていれば、`tone.policy` に加えて
`content_sources.cautions` に語句と注意書きを登録する（該当する節にだけ注意が付き、
構成・キャプション・evaluator に伝わる）。

**D. 取り込めたか確認する**

```bash
PY .claude/skills/shared/scripts/build_article_index.py --check
```

（`PY` は Python の呼び方。Windows は `py`、Mac は `python3`。`config/runtime.yaml` で決まる）

`units`（紹介ネタの数）と `by_axis`（軸ごとの内訳）を利用者に伝える。`theme-picker` は直近14日に
使った節を避けるので、**週の投稿数×2 以上**のネタ数が目安（週3投稿なら6節以上、毎日なら15節以上）。
1つの軸に偏っていたら、`strategy_axes` の `keywords` か見出しの付け方を調整する。

`content/themes.md` のストック欄はこの索引から自動生成される。手で書かない。

### 5. 自己チェックして報告する

書き終えたら、以下を自分で確認してから利用者に報告する:

- [ ] `PY .claude/skills/shared/scripts/check_brand.py` が `[ok]` を返すか（`（...）` 形式の雛形が1つも残っていないか）
- [ ] `offer.cta_line` が18文字以内か（`offer.enabled: false` の場合は不要）
- [ ] `build_article_index.py --check` が成功し、紹介ネタが週の投稿数×2 以上あるか
- [ ] `content/sources/` の文章が、利用者の確認済みの内容だけでできているか（こちらの知識で足していないか）
- [ ] `design.palette` の3色が高コントラストか（背景と文字が十分に離れているか）
- [ ] `tone.policy` の既定5項目が残っているか

報告には次を含める:

- `brand.yaml` に設定した内容の要約（読者・トーン・オファー・パレット）
- 紹介ネタの件数と軸ごとの内訳
