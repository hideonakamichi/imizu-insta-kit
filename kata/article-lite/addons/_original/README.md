# 記事制作エージェント・キット

**オウンドメディア記事自動生成キットをもとに、ひとり親支援情報にテーマを変更して、AI に専門記事を「書かせて、別の AI に査読させて、合格したものだけ公開する」ための一式です。**

勉強会の配布用に、実際に運用しているサイトから**仕組みだけ**を抜き出しました。
記事の中身・実データ・運営者情報・API キーは入っていません。

## 1. 概要

### 何をするものか

データベースに「まだ記事のないネタ」を入れておくと、

1. **執筆担当の AI** が公式サイトを調べて、対話形式の解説記事と図解画像をつくる
2. **査読担当の別の AI** が 32 項目のチェックリストと自動検査プログラムでチェックする
3. 合格したものだけがデータベースに保存され、Web サイトに公開される
4. 公開後も、点検スクリプトがリンク切れや情報の古さを拾い続ける

これを **Claude Code**（ターミナルで動く Claude。ファイルを読み書きしたりコマンドを実行したりできる）の
**サブエージェント**（親の AI が呼び出す、役割を絞った子の AI）3 体で回します。

> **このキットの出自**
> 配布された「**オウンドメディア記事自動生成**」（`hojokin-agent-distribution.zip`）をベースに、
> 実際にサイトを 1 か月運用しながら育てたものです。
> 足した部分と、その理由になった事故は **付録E** にまとめてあります。

### 全体の流れ

```
   データを入れる                              ┌──────────────────┐
   (scripts/sync-data.sh)                      │  Web サイト       │
        │                                      │  (Next.js)       │
        ▼                                      └────────▲─────────┘
  ┌───────────┐   ①記事がまだ無いものを探す  ┌──────────┐  │
  │ Supabase  │◄──────────────────────────── │  Editor    │  │
  │ (DB)      │                              │  編集長   │  │
  └────▲──────┘                              └─┬─────▲──┘  │
       │                                       │     │      │
       │ ④合格したら保存                ②書いて│     │③査読 │
       │                                       ▼     │      │
       │                                ┌──────────┐ │      │
       └────────────────────────────────│  Writer    │ │      │
                                        │  執筆担当  │ │      │
                                        └─────┬────┘ │      │
                                              │      │      │
                                              ▼      │      │
                                        ┌──────────┐ │      │
                                        │  Reviewer  │─┘      │
                                        │  査読担当  │────────┘
                                        └──────────┘
                                              │
                                     不合格なら差し戻し(最大3回)
```

| 名前 | 役割 | 使うモデル |
|---|---|---|
| **編集長** (`support-orchestrator`) | 編集長。データ同期・担当への割り振り・やり直しの管理・完了通知。**自分では記事を書かない** | opus |
| **ライター** (`support-writer`) | 執筆担当。公式サイトの調査 → 記事執筆 → 図解生成 → 4 段階の事実確認 | sonnet |
| **レビュアー** (`support-reviewer`) | 査読担当。32 項目のチェック＋自動検査。直せるものは直し、無理なものは差し戻す | sonnet |

（名前は好きに変えられます。
`.claude/agents/` のファイル名と、各ファイル冒頭の `name:` を書き換えれば動きます。）

### 配布版であることの注意

- 題材は**「ひとり親家庭が使える公的支援制度」のまま**残しています。
  ぜんぶ抽象化すると学べるものが消えるためです。**別テーマにそのまま読み替えられます**（[付録B](#付録b別テーマへの読み替え方)）。
- **実際に起きた事故の実例は、あえてそのまま残しています。** ここが一番の学びどころです（[付録A](#付録aこの仕組みの肝)）。
- 記事本文・本番データ・運営者情報・ブランド素材・API キーは**入っていません**。

## 2. できること

| できること | 担当 | 詳しい場所 |
|---|---|---|
| 公式サイトを調べて、対話形式の解説記事を書く | ライター | `.claude/skills/support-article-writer/` |
| 記事に合った図解画像を生成して貼る | ライター | 同上 |
| 32 項目＋自動検査（E01〜E24）で査読する | レビュアー | `.claude/skills/support-article-reviewer/` |
| 不合格を書き手に差し戻す（最大 3 回） | 編集長 | `.claude/skills/support-pipeline-orchestrator/` |
| 完了サマリーを Discord に通知する | 編集長 | `.claude/scripts/notify-discord.sh` |
| 公開後の記事を定期点検する（M01〜M22） | 点検スクリプト | `scripts/article_health_check.py` |
| 用語集の記事を書く（短く易しい版） | ライター/レビュアー | `.claude/skills/glossary-writer-reviewer/` |
| 当事者どうしの座談会記事を書く（倫理チェック付き） | ライター/レビュアー | `.claude/skills/roundtable-writer-reviewer/` |
| 記事を Web サイトとして表示する | Next.js | `site/` |

**E01〜E24 / M01〜M22 とは**: 事故が起きるたびに増やしてきた**自動検査の項目番号**です。
E は公開前（査読時）、M は公開後（定期点検）に走ります。
「同じ失敗を二度させない」ための仕組みで、このキットの中心です。

## 3. 必要なもの

### 3-0. 動作環境

**このキットは Windows 11 で開発し、動作確認しています。**
macOS / Linux でも動く作りですが、**確認は Windows でのみ行っています。**

| OS | 状態 | 注意点 |
|---|---|---|
| **Windows 10 / 11** | ★動作確認済み★ | シェルは **Git Bash** を使います（PowerShell や コマンドプロンプトではありません） |
| macOS | 未確認（動くはず） | 標準のターミナルでそのまま動く想定 |
| Linux | 未確認（動くはず） | 同上 |

**Windows で使う場合、ここだけ先に読んでください:**

- スクリプト（`.sh`）は **Git Bash** で実行します。Git をインストールすると付いてきます
- 本文中の `python3` は、Windows では **`python`** に読み替えてください
- `brew install` / `apt install` は macOS / Linux の書き方です。Windows は各ツールの公式インストーラを使います
- 日本語が文字化けしたら `PYTHONUTF8=1` を設定してください（詳細は「6. 注意点」）

### 3-1. インストールするツール

| ツール | 何をするもの | 入手先 |
|---|---|---|
| **Claude Code** | ターミナルで動く Claude。エージェントの実行に必須 | https://docs.claude.com/claude-code |
| **Node.js 18 以上** | Web サイト（Next.js）を動かす | https://nodejs.org |
| **Python 3** | 自動検査プログラムを動かす | https://www.python.org |
| **bash** | 付属スクリプトの実行環境 | macOS / Linux は標準。**Windows は Git Bash**（Git に付属） |
| **sqlite3** | 実行ログを貯める軽量データベース | **Windows: https://sqlite.org/download.html** / macOS 標準 / `apt install sqlite3` |
| **curl** / **jq** | HTTP 通信と JSON 整形 | **Windows: curl は標準搭載。jq は https://jqlang.github.io/jq/** / `brew install jq` / `apt install jq` |

インストール済みか確認:

```bash
# macOS / Linux
claude --version && node -v && python3 --version && sqlite3 --version && jq --version
```

```bash
# Windows（Git Bash で実行。python3 ではなく python）
claude --version && node -v && python --version && sqlite3 --version && jq --version
```

### 3-2. 取得する API キー

**API キーとは**: 外部サービスを使うための「パスワード付き利用券」です。**他人に見せないでください。**

| キー | 必須か | 何に使うか | 取得先 | 費用 |
|---|---|---|---|---|
| **Supabase の URL と service_role キー** | ★必須★ | 記事の保存先（データベース）と画像置き場 | https://supabase.com | 無料枠あり |
| **Gemini API キー** | 図解を出すなら必須 | 図解画像の生成 | https://aistudio.google.com/apikey | 無料枠あり |
| **Discord Webhook URL** | 任意 | 完了通知の投稿先 | Discord のサーバー設定 | 無料 |
| **GA4 測定 ID** | 任意 | アクセス解析 | Google Analytics | 無料 |

用語の説明:

- **Supabase**: データベースとファイル置き場をブラウザから使えるサービス。
- **service_role キー**: Supabase の**管理者用キー**。アクセス制限をすべて無視できるので、**絶対に外部に出さない**。（`anon` キーとは別物です。間違えないこと）
- **Webhook URL**: 知っている人なら誰でもそのチャンネルに投稿できる URL。**鍵と同じ扱い**にしてください。

> **一次情報の調査に外部サービスは不要です。** Claude Code が Web 取得機能を内蔵しているためです。

## 4. セットアップ手順

**上から順に実行してください。** 所要 20〜30 分程度です。

### ステップ 1: 環境変数のファイルをつくる

**環境変数とは**: API キーのような「人によって違う値」を、プログラム本体と分けて置いておく仕組みです。
このキットは、**個人情報・キー・ドメインをコードに一切書かず、すべてここから読みます。**

```bash
cp .env.example .env.local
```

`.env.local` を開くと、**上から順に 7 つのブロック**に分かれています。
各項目に「取得先」のコメントが付いているので、順番に埋めていってください。
（**空のままでよい項目**にはその旨が書いてあります）

> ⚠️ `.env.local` は `.gitignore`（Git に登録しないファイルの一覧）に入っています。**絶対に commit しないでください。**

### ステップ 2: Supabase をつくる

1. https://supabase.com にサインアップして「**New Project**」
2. 左メニューの **SQL Editor** を開き、`supabase/schema.sql` の中身を貼り付けて実行
   （**スキーマ** = テーブルの設計図。これでテーブルが作られます）
3. 動作確認用のサンプルデータも実行する:
   - `supabase/seed.sql`（3 件）
   - `supabase/seed-glossary.sql`（3 件）※用語集を使うなら
   - `supabase/seed-roundtables.sql`（1 件）※座談会を使うなら
4. 左メニューの **Storage** で「**New bucket**」→ 名前 `article-images`、**Public にチェック**
   （**バケット** = ファイル置き場のフォルダ。図解画像をここに置きます）
   - File size limit: `5 MB`
   - Allowed MIME types: `image/png,image/jpeg,image/webp`
5. **Project Settings → API** を開き、`.env.local` に貼る:

   | Supabase の画面 | `.env.local` の項目 |
   |---|---|
   | Project URL | `NEXT_PUBLIC_SUPABASE_URL` |
   | **service_role** キー（★ `anon` ではない★） | `SUPABASE_SERVICE_ROLE_KEY` |
   | 手順 4 で付けたバケット名 | `NEXT_PUBLIC_STORAGE_BUCKET` |

### ステップ 3: Gemini の API キーを取る

1. https://aistudio.google.com/apikey で「**Create API key**」
2. `.env.local` の `GEMINI_API_KEY` に貼る

図解が不要なら飛ばせますが、その場合は査読の「図解 2 枚以上」チェックに引っかかります。

### ステップ 4: サイトの基本情報を書く

`.env.local` の【3】【4】ブロックを埋めます。**ここを埋めないと、サイトの表示が「（未設定）」だらけになります。**

- `PUBLIC_SITE_URL` … 公開する URL（試すだけなら `http://localhost:3000`）
- `NEXT_PUBLIC_SITE_NAME` … サイト名
- `NEXT_PUBLIC_OPERATOR_ORG` / `NEXT_PUBLIC_OPERATOR_NAME` … 運営者

> お金や健康を扱うサイト（**YMYL** = Your Money or Your Life。人生に影響する分野）では、
> 「誰が運営しているか」の明示が検索評価でも読者の信頼でも効いてきます。

### ステップ 5: 登場人物を決める

```bash
cp config/persona.example.json config/persona.json
```

`config/persona.json` に、**質問役**（`questioner`）と**解説役**（`explainer`）の
名前・年齢・立場・口調が書かれています。自分のテーマに合わせて書き換えてください。

執筆エージェントも査読エージェントも起動時にこのファイルを読むので、
**ここを直すだけでキャラクターが差し替わります**（skill 本体を触る必要はありません）。

> 変えないほうがよいのは「質問役には専門用語を使わせない／解説役には正確性チェックを効かせる」
> という**役割の非対称性**です。これが「読みやすいのに正確」を成立させています。

### ステップ 6: Web サイトを動かしてみる

```bash
cp .env.local site/.env.local     # サイト側にも同じ値が要ります
cd site
npm install                       # 必要な部品のダウンロード（初回のみ・数十秒）
npm run dev                       # http://localhost:3000 が立ち上がる
```

ブラウザで http://localhost:3000 を開いて、ヘッダーに自分のサイト名が出れば成功です。
（記事はまだ 0 件なので、一覧は空です）

止めるときは `Ctrl + C`。次のステップに進むため、いったん止めてルートに戻ります（`cd ..`）。

### ステップ 7: データを入れる仕組みをつくる（任意・後回し可）

`scripts/sync-data.sh` は**雛形（中身が空のひな型）**です。自分のデータの入手方法に合わせて書きます。

- 外部 API やオープンデータの CSV を取り込む
- 手作業で入れる → `bash scripts/supabase-query.sh insert supports '{...}'`
- **すでに手で入れてあるなら、空のままで OK**

空でも「申込期限が過ぎたものを `closed` にする」処理だけは毎回走ります。

ステップ 2 でサンプルデータを入れたので、**まずはそのまま次に進んで構いません。**

## 5. 使い方

### 5-1. まず 1 本書かせてみる（おすすめの最初の一歩）

プロジェクトのルートで Claude Code を起動します。

```bash
claude
```

プロンプトが出たら、こう頼みます。

```
ライター (support-writer) で supports id=1 の記事を書いてください。
```

書き上がったら、査読させます。

```
レビュアー (support-reviewer) で supports id=1 の記事を査読してください。
```

★**ここで出てくる査読の指摘（E01〜E24）を眺めるのが、このキットで一番の見どころです。**★

### 5-2. パイプライン全体を自動で回す

```
編集長 (support-orchestrator) を起動して、パイプラインを 1 周回してください。
```

データ同期 → 記事がまだ無いものを抽出 → 執筆 → 査読（最大 3 回やり直し）→ 通知、まで自動で進みます。

### 5-3. 公開済み記事を点検する

```bash
bash scripts/article-health-check.sh --quick          # 数秒。ネット接続不要
bash scripts/article-health-check.sh                  # 全項目（リンク到達性を含むので時間がかかる）
bash scripts/article-health-check.sh --id 4 --id 11   # 記事を絞る
bash scripts/article-health-check.sh --images         # 図解をダウンロードして目視用リストを出す
bash scripts/article-health-check.sh --json out.json  # 結果を JSON で保存
```

終了コードは `0` = 重大な問題なし / `1` = 重大な問題あり。定期実行の失敗検知に使えます。
点検の全体像（L1〜L5 の 5 層）は `docs/article-maintenance.md` にあります。

### 5-4. データベースを直接操作する

```bash
# 読む
bash scripts/supabase-query.sh select supports "status=eq.active&select=id,title&limit=10"

# 書く（★大きい JSON は @ファイルパス で渡す★）
bash scripts/supabase-query.sh update supports @/tmp/payload.json "id=eq.10"
```

> 記事本文のような大きい JSON をコマンドの引数に直接書くと、
> OS の引数長の上限を超えて失敗します。**必ず `@ファイル` 形式**で渡してください。

### 5-5. 決まった時刻に自動実行する

**macOS**（launchd = mac の定期実行の仕組み）:

```bash
sed "s|<YOUR_PROJECT_PATH>|$(pwd)|g" .claude/launchd/com.example.support-pipeline.plist \
  > ~/Library/LaunchAgents/com.example.support-pipeline.plist
launchctl load -w ~/Library/LaunchAgents/com.example.support-pipeline.plist
```

**Linux**（cron = 定期実行の仕組み）: `.claude/launchd/cron-example.txt` を見ながら `crontab -e`

**Windows**（タスク スケジューラ = Windows の定期実行の仕組み）:

1. スタートメニューで「タスク スケジューラ」を検索して開く
2. 右側の「基本タスクの作成」→ 名前を付けて「毎日」を選ぶ
3. 「プログラムの開始」で、次を設定する

| 欄 | 入れるもの |
|---|---|
| プログラム／スクリプト | `C:/Program Files/Git/bin/bash.exe` |
| 引数の追加 | `-lc "cd '<プロジェクトのパス>' && bash scripts/run-agent.sh"` |

> パスは `\` ではなく `/` で書いても動きます（そのほうが打ち間違いが減ります）。
> `<プロジェクトのパス>` は、このフォルダを置いた場所に置き換えてください。
> **パスに日本語やスペースが含まれる場合は、上のようにシングルクォートで囲みます。**

★注意★ **PC がスリープしていると動きません。**
確実に毎日動かしたいなら、タスクの「条件」タブで
「タスクを実行するためにスリープを解除する」にチェックを入れるか、
クラウド（GitHub Actions など）での実行を検討してください。

### 実行の記録を見る（ダッシュボード）

エージェントは動くたびに `.claude/db/agents.db` に記録を残します（`scripts/start-reflection.sh` が書き込み）。
それを 1 枚の HTML にまとめます。

```bash
python scripts/dashboard.py          # dashboard.html を作る
python scripts/dashboard.py --open   # 作ってブラウザで開く
```

- **標準の Python だけで動きます**（`pip install` 不要）
- 出力は**自己完結した HTML 1 枚**。サーバも要らず、そのまま人に渡せます
- 記録がまだ無くても落ちません

見えるもの: 実行回数・完了率・のべ稼働時間 / 担当別の実行数と平均スコア /
品質スコアの推移（下がった点＝差し戻しが起きた回）/ **エージェント自身が書いた改善メモ** /
直近の実行と親子関係 / エラー。

> 担当別の表で、**査読の実行数が執筆より多ければ差し戻しが起きています**。
> 2 つが同数に近いほど「一発合格」が多い、と読めます。

## 6. 注意点

### 6-1. 秘密情報の扱い

- **`service_role` キーはアクセス制限をすべて無視できます。** ブラウザ側に出さないでください。
  `site/lib/supabase.js` はサーバー側専用です。
- `.env.local` と `site/.env.local` は `.gitignore` 済みです。**この設定を外さないでください。**
- **誰かに配る前に必ず確認**: `.env` 系のファイルが混ざっていないか、`.git` の履歴にキーが残っていないか。

### 6-2. お金・健康を扱うときの守りかた（YMYL）

- **断定しない。** 「もらえます」ではなく「対象になる場合があります」。
- **必ず窓口確認への導線を添える。** 個別の可否は AI には判断できません。
- **いつ時点の情報かを明記する。** 制度は変わります（`M07` / `M09` が古さを検出します）。
- 記事は「知る入口」であって「判断の根拠」ではない、という位置づけを崩さないこと。

### 6-3. うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| `Supabase の環境変数が設定されていません` | `cp .env.example .env.local` → 値を埋める → `cp .env.local site/.env.local` |
| サイトのヘッダーが「サイト名（未設定）」 | `.env.local` の【3】【4】ブロックが空。埋めて再起動 |
| `Failed to parse URL from undefined/...` | 同上（環境変数が読めていない）。`site/.env.local` を忘れていないか確認 |
| `DISCORD_WEBHOOK_URL not set, skipping` | 通知を使わないなら**正常**。無視して OK |
| 図解画像が記事に入らない | ①バケットが **Public** か ②Gemini キーが有効か ③`service_role` キーで書き込めるか |
| `claude` コマンドが定期実行から見つからない | `scripts/run-agent.sh` の `claude` を絶対パスに書き換える。plist の `EnvironmentVariables` で `PATH` を足す |
| サブエージェントの実行ログが親に紐づかない | 親が子を呼ぶときのプロンプト先頭で `PARENT_RUN_ID={自分の AGENT_RUN_ID}` を渡す |
| 大きい JSON の更新が失敗する | `supabase-query.sh` に `@ファイルパス` 形式で渡す |
| Windows で日本語が文字化けする | `PYTHONIOENCODING=utf-8` と `PYTHONUTF8=1` を設定（`article-health-check.sh` は設定済み）。curl は `-d` ではなく `--data-binary @file` を使う |
| 検査ルールを足したら検出数が想定外に動いた | ★変更前のスクリプトを同じデータに対して走らせ、差分を数字で比較する★ |

### 6-4. 運用のコツ

- **やり直しは 3 回で打ち切る。** それ以上は人間が見たほうが早いです。
- **通知は 1 日 1 回まとめて。** 個別の成功通知が流れると、失敗が埋もれます。
- **`--quick` を高頻度で、フル点検は低頻度で。** リンク到達性チェックは時間がかかります。
- **検査項目を増やすときは、既存項目への影響を必ず数字で確認する。**

# 付録A：この仕組みの肝

★ここが、参加者にいちばん持ち帰ってほしい部分です。★

## A-1. 執筆担当と査読担当を分ける

**1 体の AI に「書いて、自分でチェックして」と頼んでも、自分の誤りには気づけません。**
書いたときの前提を持ったまま読み直すので、同じ思い込みが素通りします。

そこで **執筆と査読をまったく別のサブエージェント**にし、査読担当には
**記事本文とチェックリストだけ**を渡します。執筆担当がどう考えたかは渡しません。

さらに徹底していること:

- **編集長が自分で書くことを禁止。** 書くと査読が身内チェックになります。
- **執筆担当と査読担当は通知を出さない。** 通知は編集長がまとめて 1 回。
- **差し戻しは最大 3 回。** 永久ループを防ぎます。

> 実装は `.claude/agents/*.md`（人格と契約だけの薄いラッパー）と
> `.claude/skills/*/SKILL.md`（実行手順の本体）に分かれています。
> agent の先頭に `skills: [...]` と書くと、起動時に自動で読み込まれます。

## A-2. 事故が起きるたびに、skill にルールを足し、機械検出を足す

品質は「気をつける」では上がりません。1 回でも事故が起きたら、必ず 2 つやります。

1. **skill（自然言語の手順書）に、実例つきで追記する** — 「❌ こう書いた／✅ こう書くべきだった」の形で
2. **機械で検出できる形にしてコードに足す** — 正規表現でも件数チェックでもよい

その結果:

| 層 | 実装 | 番号 | いつ走るか |
|---|---|---|---|
| 公開前の検査 | `support-article-reviewer/SKILL.md` の `check_article()` | **E01〜E24** | 査読のたび |
| 公開後の点検 | `scripts/article_health_check.py` | **M01〜M22** | 定期実行 / 手動 |

一度書いたルールは**忘れません**。人間のレビューと違って疲れません。

## A-3. ★実際に起きた事故（3 つ）★

抽象論ではなく、本当に起きたものです。

### 事故 1: 「毎月お金が入る」と書いたが、実際は奇数月だった

制度をやさしく言い換えようとして、要約にこう書いていました。

> ❌ シングルマザー・シングルファーザーの家庭に**毎月お金が入る**制度。

実際は **奇数月に年 6 回、2 か月分ずつまとめて**振り込まれます。
「毎月入る」と信じて家計を組んだ読者は、その月に困ります。

> ✅ 第1子は月額最大 48,050 円で、**支払いは奇数月に年 6 回、2 か月分ずつまとめて振り込まれます**。

さらに厄介だったのは、**記事本文は正しく書けていた**のに、
**あとから書き直したタイトルと要約だけ**が誤りを持ち込んでいたことです。

**対策**:
- 「やさしく言い換えるときに正確性を落としやすい表現」を**危険語**として定義し、`E24` / `M20` で検出
- 本当に毎月の制度もあるので、**禁止ではなく警告**（「再確認せよ」のシグナル）にした
- ★**この検査は解説役（専門家キャラ）の発言も対象**★
  読みやすさの検査（`E20`）は専門家を対象外にしていますが、
  正確性の話は**専門家の口から出た誤りこそ読者に最も信じられてしまう**ので、例外を作りませんでした
- **記事を直したあとにタイトル・要約を書き直すときも、同じ事実確認をやり直す**ルールを追記

### 事故 2: 図解画像 26 枚のうち 10 枚が、別の制度の画像だった

生成した図解を保存する過程で、**他の記事の画像 URL がそのまま貼られていました**。
絵の中身は機械では判定できないので、長いあいだ気づけませんでした。

**対策** — 「中身は判定できなくても、周辺は機械で拾える」と考え直しました。

- ファイル名に `{記事id}-` の命名規則を課し、合わないものを警告（`M18`）
- 同じ画像 URL を 2 つの記事が共有していたら重大エラー
- 画像データのハッシュ値が別記事と一致したら重大エラー
- それでも中身は見るしかないので、`--images` で画像をダウンロードして**目視用リスト**を出す（`M14`）

**教訓**: 「機械では判定できない」で止めない。**判定できる代理指標を探す。**
それでも残る部分は「人が見るべきリスト」として明示的に吐き出す。

### 事故 3: 「多くの自治体では」を 7 箇所直した直後、語順を変えて復活した

根拠なく全国の傾向を語る表現（`E19` / `M06`）は検出していましたが、
**完全一致のパターンだった**ため、査読で 7 箇所直した直後に
**「対象になっている自治体が多い」**という語順で復活しました。
さらに、**1 つの市の締切しか調べていないのに**「締切が早いことが多い」が 4 箇所で反復されていました。

**対策**:
- パターンを 9 → 20 に拡張（`自治体が多い` / `ことが多い` / `のが通例` / `増えています` / `たいてい` / `大半` …）
- ★ただし「おおむね」は入れなかった★ — 「おおむね136万円以下」のような**金額の概算**に使われ、
  全国傾向の主張ではないため。実際に入れたら誤検出が 7 件出ました
- 同じ文に具体例や出典（`◯◯市では` / 統計 / URL / 省庁名）があれば警告度を下げる。
  **禁止ではなく「根拠を示せ」**にするため
- 執筆側の skill にも実例を追記: **「1 自治体しか見ていないなら『◯◯市では』までしか書けない」**

**教訓**: 検出パターンは**必ずすり抜けます**。すり抜けた実例が出たら、その形を足す。
そして**緩和ルールを入れるときは、他の検査に波及しないか数字で確認する**
（このときも、共通の緩和処理に入れたら別の検査の件数まで動いてしまい、対象を限定しました）。

## A-4. 一次情報で必ず裏を取る

- 執筆前に**必ず公式サイト（省庁・自治体）に当たる**。まとめサイトは根拠にしない。
- 調べた根拠は `research_notes`（JSON）に**引用元 URL と引用文つき**で残す。
- 査読担当は `research_notes` と本文を**突き合わせ**、本文の数字が根拠に実在するか確認する。
- **「1 自治体しか見ていないなら、その自治体の名前までしか書けない」**（事故 3 の教訓）

## A-5. 外部レビューの指摘も鵜呑みにしない

別の AI に記事をレビューさせると、それらしい指摘が返ってきます。**が、間違っていることがあります。**
実際に、指摘に従って直そうとしたら、**一次情報を確認すると元の記述のほうが正しかった**ことがありました。

そこで点検フローに **L5「外部レビュー指摘の一次情報検証」** という層を置いています。
**指摘 → 一次情報で検証 → それから直す**の順を崩しません。

**自分のエージェントが書いたものも、他人（他 AI）が指摘したものも、扱いは同じです。**
一次情報だけが判断基準です。
