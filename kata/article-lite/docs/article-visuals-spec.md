### 1-1. ★表示サイズについての重要な検証結果★

指示は「実表示 32〜40px」だったが、**実際に 32px / 40px に縮小して目視した結果、32px では表情差がほとんど判別できない**。

| 表示サイズ | みさき 3種の判別 | 藤井 2種の判別 |
|---|---|---|
| 32px | △ 納得(口を開けた笑顔)のみ分かる。通常と困り顔はほぼ同じに見える | ✕ 判別不能 |
| 40px | ○ 3種とも判別できる | △ 口の直線 vs 曲線でかろうじて分かる |
| 48px | ◎ 明確 | ○ 分かる |

**推奨: アイコンの表示サイズは 44〜48px にする。** 32px にすると表情バリエーションを作った意味がほぼ失われる。
スマホで幅が厳しい場合でも 40px を下限にしたい。

藤井の `通常` と `注意` は 40px でも差が小さい。これは意図的なトレードオフで、
**判別しやすい「怒り顔」を一度生成したが、読者を責めるトーンになるため不採用にした**
(このサイトは「かわいそうトーン禁止」「読者を追い詰める表現禁止」が原則)。
`注意` の意味は隣接する `:::warning` ボックスが担うので、アイコンは補助と考えるのが妥当。

### 1-2. 表情の出し分けルール (機械判定)

**大原則: 判定を外すと表情と内容がちぐはぐになって逆効果。確信が持てなければ `通常` に落とす。**

判定は「1つの吹き出し (話者記法 `**みさき**:` 〜 次の話者記法まで) の本文テキスト」を対象にする。

#### みさき (3種)

上から順に評価し、最初に当たったものを採用。どれにも当たらなければ `misaki-normal`。

| 優先 | 条件 (すべて満たす) | 表情 |
|---|---|---|
| 1 | 本文に **納得語** を含む　かつ　**不安語を含まない** | `misaki-nattoku` |
| 2 | 本文が `？` または `?` を含む　かつ　**不安語** を含む | `misaki-komari` |
| 3 | 上記以外 | `misaki-normal` |

- **納得語** (完全一致で検索する語のリスト):
  `なるほど` / `そうなんですね` / `そうなんだ` / `助かります` / `ありがとうございます` /
  `よかった` / `安心しました` / `わかりました` / `それなら` / `心強い`
- **不安語**:
  `不安` / `心配` / `わからな` / `分からな` / `難しそう` / `どうしよう` / `大変` /
  `困っ` / `間に合う` / `間に合わ` / `できるのかな` / `自信がな` / `ややこしい`

補足:
- 条件 1 で不安語を除外しているのは「なるほど、でも不安です」型の発言で納得顔が出るのを防ぐため。
- 条件 2 で `？` を必須にしているのは、不安語を含むだけの平叙文 (制度説明の引用など) で困り顔が出るのを防ぐため。
- **記事の最初のみさき発言は必ず `misaki-normal` にする**。冒頭からいきなり困り顔だと導入の印象が重くなる。

#### 藤井先生 (2種)

| 優先 | 条件 | 表情 |
|---|---|---|
| 1 | 本文に **注意語** を含む | `fujii-chui` |
| 2 | 上記以外 | `fujii-normal` |

- **注意語**:
  `注意` / `気をつけ` / `忘れずに` / `忘れると` / `期限` / `締切` / `締め切り` /
  `失権` / `支給停止` / `資格を失` / `打ち切` / `受けられなくなり` / `対象外` /
  `必ず` / `絶対に` / `間に合わないと` / `遅れると`

補足:
- `必ず` は藤井の発言で頻出するので、注意顔が出すぎるようなら真っ先に外す候補。
  運用してみて `fujii-chui` の出現率が藤井の全発言の 25% を超えるようなら `必ず` を削る。
- `:::warning` ディレクティブの直前・直後の藤井発言は無条件で `fujii-chui` にする、という
  ルールを足してもよい (本文語句に依存しないぶん誤判定が起きにくい)。

#### あかり

`akari-normal` のみ。座談会記事で使用。

### 1-3. 実装上の注意

- 画像は**不透明背景**なので、丸く見せるには表示側で `border-radius: 50%` を当てる。
- 顔の中心は画像のやや上寄り。丸くクリップしても顔は切れない。
- 6枚とも背景色を `#FAEEEE` に揃えてあるので、並べても背景の段差は出ない。

### 2-1. ★指示は10種だったが11種にした理由★

DB の全記事 (15本・H2 158個) を抽出して分類したところ、
**「併用できる他の支援制度」系の見出しが 23 個あり、単独で最多だった**。
指定の10分類にはこれに当たるものがなく、そのまま作ると

- 15記事中13記事で、記事の終盤の1セクションだけイラストが欠ける
- 「よくある質問」の直前という目立つ位置に穴が開く

ことになるため、`related` を11種目として追加した。不要なら使わなければよい (他10枚に影響しない)。

### 2-2. 画風とロゴとの整合

- 既存キャラクターイラストと同じ「細い濃茶の輪郭線 + フラット塗り + 影なし + 丸みのある形」で統一。
- ブランド色 `#e05a7a` / `#b23a57` / アクセント `#FACC15` を全11枚に使用。
- 新ロゴ `site/public/brand/logo-mark-trim.png` (親が子を抱えるシンボル) は
  **輪郭線のない単色ベタのピクトグラム**で、線画である見出しイラストとは描画レイヤーが違う。
  ただし `eligibility` を**顔を描かない人型シルエット**にしてあるため、
  「人を単色のシルエットで表す」という語彙はロゴと共通しており、並べても違和感はない。
  色も `#b23a57` 系で揃っている。

### 2-3. ★画像内テキストについて★

**11枚すべて、文字 (漢字・かな・英数字) はゼロ**。拡大して目視確認済み。
書類・吹き出し・本のページは「意味のない横線」、カレンダーは「日付のない丸のグリッド」、
時計は「数字のない目盛り」、お札は「無地の長方形」で表現している。
これにより千葉・大阪へ展開しても、年度が変わっても、画像を作り直す必要がない。

**1つだけ例外がある**: `caution.png` の警告三角形の中に**感嘆符 `!` のピクトグラム**が入っている。
これは文字ではなく ISO 7010 (W001) の警告標識記号であり、言語に依存しないため許容した。
「文字ゼロを厳密に貫きたい」場合は三角形のみのバージョンに差し替え可能。

### 2-4. 見出し → イラストの割り当てルール

H2 の文言だけから機械的に決める。**2段階**で判定する。

#### ステージA: 決定的パターン (この順に評価し、最初に当たったものを採用)

| 順 | 分類 | 含まれていれば確定するキーワード |
|---|---|---|
| 1 | `faq` | `よくある質問` `Q&A` `質問と答え` |
| 2 | `summary` | `基本情報` `まとめ` |
| 3 | `related` | `併用` `併給` `あわせて使える` `あわせて利用` `他にも使える` `他の支援制度` `参考リンク` `一緒にできる` `関連` |
| 4 | `overview` | `ってどんな制度` `どんな制度` `どういう制度` `制度か` `仕組み` `何をしてくれる` `ではなく` |

#### ステージB: 位置による判定

ステージAで決まらなければ、下表のキーワードを全部探し、
**見出しの中で最も先に登場したキーワード**の分類を採用する
(同位置なら表の上の行が優先)。

| 分類 | キーワード |
|---|---|
| `documents` | `必要書類` `必要な書類` `そろえる` `持ち物` `用意するもの` |
| `flow` | `流れ` `申請方法` `手続き` `申し込み` `申込` `ステップ` `再申請` |
| `schedule` | `スケジュール` `支給期間` `時期` `期限` `タイミング` `支給月` `振込` `更新` `いつ` `以降` `続くのか` |
| `income-limit` | `所得制限` `所得要件` `所得の目安` `所得基準` `所得について` |
| `eligibility` | `対象` `条件` `誰が` `誰?` `誰？` `受給要件` `納付要件` `資格` `世帯` `お子さん` `どんなとき` `ならない人` |
| `amount` | `いくら` `支給額` `金額` `給付額` `限度額` `上限額` `総額` `控除額` `利用料` `家賃` `月額` `早見表` `安くなる` `無利子` `負担` |
| `related` | `との違い` `どう違う` `との関係` `選択肢` |
| `caution` | `注意` `気をつけ` `知っておき` `確認しておきたい` `見落と` |

**なぜ「位置」で決めるのか**: 「申請の流れと必要書類」のような複合見出しで、
主題である先頭の語を採用するため。これにより
「必要書類と申請方法」→ `documents` / 「申請の流れと必要書類」→ `flow` と自然に分かれる。

**なぜステージAを分けたのか**: 位置だけで判定すると
「マル親医療費**助成**ってどんな制度?」が `助成`(amount) に取られて `overview` にならない。
制度の性格を決定づける語だけを先に確定させている。

#### フォールバック

どれにも当たらない場合:

- **記事の最初の H2** であれば `overview` を出す
- それ以外は**イラストを出さない**

★間違ったランドマークを置くのは、置かないより悪い★ ので、無理に埋めない設計にした。

### 2-6. 取りこぼしの傾向と、今後の記事執筆への申し送り

未分類7件を見ると、取りこぼすのは次のパターン:

1. **制度の下位プログラム名をそのまま H2 にしている** (`修了支援給付金について` 等)
2. **その制度だけの独自トピック** (`「第3子」の数え方` `自治体で見られる主な制度例`)
3. **体言止めでない、主張の文** (`事前相談は絶対に必須です`)

今後の記事執筆時に、H2 に上表のキーワードをひとつ含めるだけで拾えるようになる。
たとえば `修了支援給付金について` → `修了支援給付金はいくら？` にすれば `amount` が当たる。
`support-article-writer` skill に「H2 には割り当てキーワードを1語入れる」を足すと網羅率が上がる。

## 3. 目次にも同じイラストを小さく並べる案

**結論: 有効。実装を推奨する。**

「長いページのどのあたりだったか記憶に残るランドマークにしたい」という狙いに対して、
目次と本文で同じ絵を出すのは効果が大きい。目次で一度見た絵が本文で再登場することで、
読者の中に「絵 ↔ 節」の対応が作られ、スクロール中に位置を掴めるようになる。

### 実現可能性

検証として、11枚を **210×52px 相当**まで縮小して並べた。この大きさでも
**11種すべてが互いに判別できた**。モチーフの輪郭 (三角形 / 吹き出し / 棒グラフ / カレンダー /
人型 / 放射状) が十分違うため、小さくしても潰れない。追加素材は不要で、同じ PNG を流用できる。

### 注意点

1. **目次では正方形に切らないこと。** 1200×300 の横長を正方形にクロップするとモチーフが切れる。
   横長のまま幅 40〜64px 程度の小さいバナーとして置くか、`object-fit: contain` を使う。
2. **背景色が目次の行の背景と干渉する。** 11枚とも背景が淡い色で塗られているので、
   目次の行に並べると「色のついた小さい帯」が縦に11本並ぶ。
   これは**むしろ狙いに合う** (色でも位置を覚えられる) が、目次全体がにぎやかになりすぎる場合は
   角丸 4px + 少し彩度を落とす CSS フィルタをかけるとなじむ。
3. **未分類の H2 は目次でも絵なしになる。** 目次の行だけインデントがずれて見えないよう、
   絵がない行にも同じサイズの空きボックスを確保する。
4. **画像点数が増える。** 目次に11枚 + 本文に11枚だが、**URL は同一なのでリクエストは11本**。
   ブラウザキャッシュが効くので実質コストは増えない。目次側は `loading="lazy"` を付けない
   (ファーストビューに近いため)。
5. **スマホ幅では目次が窮屈になる。** 幅 375px だと「絵 + 見出しテキスト」で1行が厳しい。
   モバイルでは目次の絵を出さない、あるいは 24px まで小さくする判断が要る。
   24px でも「三角形」「吹き出し」「棒グラフ」レベルの区別はつく。

## 4. alt テキストの扱い

**結論: 見出しイラストは `alt=""` + `aria-hidden="true"`。キャラクターアイコンも `alt=""` + `aria-hidden="true"`。**

### 見出しイラスト

- これらは**純粋な装飾**である。イラストが持つ情報 (「ここは金額の節です」) は、
  直後の H2 見出しのテキストが**すでに完全に伝えている**。
- ここに `alt="金額のイラスト"` のような説明を入れると、スクリーンリーダーの読者は
  「金額のイラスト」「支給額はいくら？」と**同じ意味を2回聞かされる**ことになり、
  ただのノイズになる。記事は H2 が11個あるので、11回繰り返されることになる。
- WAI の Web Accessibility Tutorials でも、隣接テキストと重複する装飾画像は
  空 alt にすべきとされている。
- したがって `alt=""` を付け、さらに `aria-hidden="true"` を足して支援技術から完全に外す。

```html
<img src="{BASE}/sections/amount.png" alt="" aria-hidden="true" width="1200" height="300">
```

- SEO 上の損失もない。画像検索からの流入を狙う画像ではなく、
  そもそも**全記事で同じ画像を使い回す**ので個別記事のシグナルにはならない。

### キャラクターアイコン

- 吹き出しには `**みさき**:` `**藤井**:` という話者名が**テキストとして併記される**。
  アイコンに `alt="みさき"` を付けると話者名が2回読まれる。
- したがってこちらも `alt=""` + `aria-hidden="true"` とし、
  **話者名はテキストで出す** (視覚的に隠す場合も `.sr-only` などで読み上げには残す)。
- これにより「誰が話しているか」はテキストが、「親しみやすさ」は画像が、と役割が分かれる。

### 例外

将来、**イラストだけが持つ情報**を載せた図 (支給額の早見表を図解したもの等) を作る場合は、
装飾ではないので必ず内容を説明する alt を書く。本仕様書の17枚は全て装飾。

## 5. クレジット表記

サイト名がひらがなに統一されたため、表記は以下で確定:

```
© くらしの支援ガイド（サンプル）
```

- ★サイト名は自分のサイトのものに差し替えてください（表記ゆれを作らないこと）。★
- 実際に入れる文字列は、ドメインも併記する:
  `© くらしの支援ガイド（サンプル）  example.com`

### ★2026-07-27 方針変更: CSS で重ねる → 画像に焼き込む★

当初この節は「**画像には一切焼き込まない。表示側の CSS で右下に重ねる**」と書いていた。
理由は ①サイト名が変わるたびに17枚を作り直すことになる ②画像内文字は Gemini が崩す
事故の温床 ③CSS ならあとから変えられる、の3点だった。

**しかしユーザーの指摘で、この方針は目的を果たさないと判明した。**

> 画像の上においたテキストですか？それだと意味ないのでは？DLされたときに

そのとおりで、**CSS で重ねたクレジットは、画像を右クリック保存した人には残らない**。
出てくるのは元の PNG である。クレジットを入れる一番の目的 (画像だけ持ち出されたときに
出所を残す) がまったく果たせていなかった。

理由②も前提が間違っていた。**Gemini に描かせる必要はない。**
出来上がった画像に PIL でテキストを合成すれば、文字が崩れることは原理的にありえない。
理由①も、スクリプトを1回実行するだけで11枚を作り直せるので障害にならない。

**現在の方式: PIL で画像の下端に焼き込む。**

```python
font = ImageFont.truetype(r"C:\Windows\Fonts\YuGothM.ttc", 20, index=0)
d.text((w - tw - 18, h - th - 16), TEXT, font=font, fill=(120, 92, 86))
```

焼く位置を**下端**にしているのがポイント。表示側は `aspect-ratio: 5.5/1` +
`object-fit: cover` で上下を切るため、**サイト上ではクレジットが切り取られて見えず、
ダウンロードされた画像には残る**。絵は邪魔されず、目的も果たせる。

- 吹き出しのキャラクターアイコンには**付けない**。小さすぎて成立しない
- 制度ごとに作る図解 (金額の早見表など) に付けるかは別途判断する

統合済みの表示側 CSS (`site/app/globals.css`):

```css
/* イラストと H2 を1つの塊として見せる (別々だとピンクのブロックが2つ並んで
   中途半端に見え、高さも食う) */
.article .article-visual { margin: 2.4em 0 0; border-radius: 12px 12px 0 0; overflow: hidden; }
.article .article-visual + h2 { margin-top: 0; border-radius: 0 0 12px 12px; }

/* ★高さは px で固定せず比率で切る★
   px 固定だと幅が広いほど切り取る割合が増え、PC で人物の頭が切れる。
   素材11枚の実測: 絵は上下に 12% ずつ余白があり高さの 75% を使う
   = 切れるのは 1200:226 ≒ 5.3:1 が限界。安全側に 5.5:1 とする */
.article .article-visual img { aspect-ratio: 5.5 / 1; object-fit: cover; }
```

注意点:

- 背景が淡い11色それぞれの上に載るので、**濃い茶系の半透明**にすると全色で読める。
  白抜きにすると淡い背景では消える。
- 吹き出しのキャラクターアイコン (32〜48px) には**付けない**。小さすぎて成立しない。
  クレジットは見出しイラストにのみ付ける。
- `content` はテキスト選択・コピーの対象外になるため、
  クレジットを確実に残したい意図には合う (画像だけ抜かれた場合は守れない点は同じ)。

## 6. 制作メモ (skill へのフィードバック用)

### 生成回数と発生した崩れ

| 対象 | 成功までの生成回数 | 起きた問題 |
|---|---|---|
| キャラクター6枚 (初回) | 1回 | 全員同一人物として成功。ただし**構図の寄り具合が6枚でバラバラ**になった |
| キャラクターの構図統一 | 生成しなおさず**PIL でトリミング**して解決 | — |
| みさき困り顔・納得顔 | 2回目で採用 | 1回目は表情が弱く 32px で判別不能。困り顔は生成時に**背景が勝手にラベンダー色**になった |
| 藤井 注意顔 | 3回目で採用 | 2回目は眉が太いV字 + 眉間のたてじわで**怒り顔**になった。3回目で「たてじわ禁止・V字禁止」を明記して解決 |
| 見出しイラスト11枚 (初回) | 1回で8枚成功 | `caution` に**指示していない吹き出しが入り** `faq` と似た。`summary` と `eligibility` が**どちらも緑の丸+白チェック**になり酷似 |
| eligibility / caution / summary | 2回目で採用 | 「★チェックマークを描いてはいけません★」「★吹き出しを描いてはいけません★」と**名指しで禁止**して解決 |

### 得られた教訓 (`support-article-writer` skill の画像ルールに追記する価値があるもの)

1. **人物の構図・寸法は生成で揃えようとせず、生成後に PIL でトリミングして揃える。**
   同じプロンプトでも寄り具合は毎回変わる。顔の上端・下端の位置を目視で決めて
   「顔が画像の N% を占める」ように機械的に切ると、6枚が完全に揃う。
   これは image-to-image の同一人物性を1ミリも損なわない。

2. **複数枚のセットを作るときは「他の絵に描いたモチーフ」を名指しで禁止する。**
   個別に見れば正しい絵でも、セットとして並べると被る。
   今回は「チェックマーク」「吹き出し」が2枚ずつに出て衝突した。
   セット生成では、モチーフ一覧を先に決めて、各プロンプトに
   「★このモチーフは描いてはいけません★」を入れるとよい。

3. **背景色は生成に任せず、生成後に塗り替える。**
   同じ「淡いピンク」指示でも1枚だけ紫になることがある。
   四隅からシードを取って**外周から flood fill** すれば安全に統一できる。
   ただし**許容誤差を白より小さく**すること (白いシャツを背景と誤認して消す事故が実際に起きた。
   背景 `(250,238,238)` と白の距離は 18 なので、許容誤差は 10 程度にする)。

4. **表情の「強さ」と「トーン」はトレードオフになる。**
   小さく表示して判別させようとして表情を強調すると、
   注意顔は怒り顔に、困り顔は泣き顔に寄る。
   このサイトは読者を責めない・追い詰めないトーンが原則なので、
   **判別性を少し犠牲にしてでも穏やかな側を選ぶ**。
   判別性は表示サイズを上げる (32px → 44px) ことで取り返すほうが副作用がない。

5. **「画像内に文字を描かない」は極めて有効。**
   今回17枚すべてで文字関連の事故がゼロだった。
   ポイントは禁止を**具体的な描画対象にまで下ろす**こと:
   「本のページ・書類・カレンダー・時計の文字盤・看板・お札にも文字を書かず、
   無地または意味のない横線にする」と書くと、Gemini は素直に従う。

6. **横長バナーは 21:9 で生成して、モチーフを切り出して目的の比率に再配置する。**
   Gemini の `imageConfig.aspectRatio` は 21:9 (実測 1584×672) までで 4:1 は作れない。
   中央クロップだと絵の上下が切れる (実際 `overview` の電球の光線が切れる寸前だった)。
   **モチーフの外接矩形を取り出して新しいキャンバスに一定サイズで貼る**と、
   目的の比率が正確に出て、かつ全枚数でモチーフの大きさが揃う。
