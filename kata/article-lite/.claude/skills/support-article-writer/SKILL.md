# ひとり親支援記事執筆手順 (ライター専用)

ひとり親支援制度 (supports テーブル) の対話形式記事 (article_md / article_title / research_notes) を生成する詳細プロトコル。レビューはレビュアー (`support-reviewer`) が担当する。

## Mission

| 項目 | 内容 |
|---|---|
| 目的 | ひとり親支援制度の対話形式記事を高品質に執筆 |
| KPI | 記事の情報量 (10,000 文字以上)、ファクトチェック通過率、レビュー一発合格率 |
| 責任 | DB 内の制度データ + Web 調査 (WebFetch/WebSearch) を元に、正確で読みやすい対話形式記事を書く |

## 対象範囲の書き分け (★target_scope 別・全記事必須★)

supports テーブルの `target_scope` を必ず確認し、記事の冒頭 (最初の3往復以内) で対象範囲を明示する:

| target_scope | 意味 | 書き方 |
|---|---|---|
| `hitorioya` | ひとり親専用の制度 | 通常どおり。母子/父子両対象を明記 |
| `all_families` | 子育て世帯全般の制度 | ★「ひとり親専用の制度ではなく、すべての子育て家庭が対象」を冒頭で明言★。その上で「ひとり親目線での活用法」(併給できるひとり親専用制度への内部リンク、ひとり親だと有利になる点等) を厚く書き、単なる一般子育て記事にしない |
| `bereaved` | 死別のみ対象 | 「死別によるひとり親家庭が対象 (離婚は対象外)」を冒頭で明言。離婚ひとり親向けの代替制度に内部リンク |

target_scope が NULL の場合は Web 調査で対象範囲を確定し、DB に UPDATE してから執筆する。

## SEO 同義語ルール (★2026-07-25 追加・全記事必須★)

検索者は「シングルマザー」「シンママ」で探し、制度は「ひとり親」で書かれている。このギャップを埋めるため、**役割分担で同義語を自然に散りばめる**:

- **解説役 (`explainer`) = 制度用語**: 「ひとり親」「母子家庭・父子家庭」(制度名は正式名称のまま)
- **質問役 (`questioner`) = 口語**: 「シングルマザー」を自然に使う。「シンママ」は記事全体で1回程度まで (YMYL なので乱発しない。例:「シンママ仲間から聞いたんですけど…」)

> ★この同義語リストは題材依存です。★ 別テーマに移すときは
> 「検索者が打つ言葉」と「業界の正式用語」のペアに置き換えてください
> (口語は質問役、正式用語は解説役、という役割分担だけを引き継ぐ)。
- 各記事の本文に**最低1回ずつ**含める: 「シングルマザー」「母子家庭」「父子家庭 (またはシングルファーザー)」
- **summary (meta description になる) に「シングルマザー」を含める** (DB の summary カラム更新時)
- FAQ の質問文は検索クエリに寄せる (例:「シングルマザーですが〜はもらえますか？」)
- 見出し (H2) への挿入は自然な場合のみ。キーワード詰め込みはしない

## 読者への配慮 (★このサイト固有・全記事共通★)

読者は時間もお金も余裕がないことが多いひとり親。以下を厳守:

- **結論ファースト**: いくらもらえる/借りられる/安くなるかを記事の早い段階で明示
- **離婚・死別の事情に踏み込まない**: 制度の説明に必要な範囲以上に家庭事情を描写しない
- **母子家庭・父子家庭の両方が対象であることを必ず明記** (対象が限定される制度は限定と明記)
- **「かわいそう」トーン禁止**: 同情ではなく実用情報。当事者を追い詰める表現 (「〜しないと損」の煽り連発等) も禁止
- **窓口に行く前に何を準備するか**が分かる状態をゴールにする

## 読者の言葉で書くルール (★2026-07-26 追加・全記事必須★)

### なぜこのルールが要るのか (背景・必ず読むこと)

**この skill 群は、もともと補助金エージェント (経営者向け) から派生した。** そのため語彙が制度側・役所側に寄ったまま残っている。ところが**このサイトの読者は、その対極にいる**。時間もお金も余裕がなく、疲れて片手でスクロールしているひとり親だ。

実際に起きていた事故 (supports id=1 の旧 `summary`):

> ひとり親家庭の生活の安定と自立の促進のために支給される手当。18歳到達後最初の3月31日までの児童を養育する母・父・養育者が対象。

これは児童扶養手当法 第1条の**目的規定をほぼ写しただけ**で、読者には何も伝わらない。「自分がいくらもらえるのか」「うちは対象なのか」が 1 秒で分からない文章は、読まれずに閉じられる。

**理由が分からないルールは守られない。** だから覚えるべきは表の丸暗記ではなく、次の一点:
**制度が何をするか (制度側の視点) ではなく、読者の生活がどう変わるか (読者側の視点) で書く。**

### どこに適用するか (適用範囲)

| 対象 | 適用 | 理由 |
|---|---|---|
| `article_title` | ★必須★ | 検索結果と一覧で最初に読まれる |
| `summary` | ★必須★ | トップのカード説明文 + meta description になる |
| 記事本文の**質問役 (`questioner`) の発言** | ★必須★ | 質問役は読者代理。読者が使わない語を使わせない |
| 記事本文の**見出し (H2/H3)** | ★必須★ | 拾い読みの導線。ここが役所語だと本文まで進まない |
| 記事本文の**解説役 (`explainer`) の解説** | 対象外 | 役割上むしろ正確であるべき。制度用語を使ってよい |
| `:::pointbox` / `:::warning` / テーブル | 準用 | 正式名称・法令要件はそのまま。地の説明文は平易に |

> 解説役が制度用語を使うときは、**初出で質問役が「それってどういう意味ですか？」と聞き返す**か、解説役自身がかっこで補足する形にすると、正確さと平易さを両立できる。

### ★崩してはいけないもの (例外)★

平易にするのは**説明**であって**事実ではない**。以下は言い換え・省略・丸めを禁止する:

- **制度の正式名称** — 略さない・言い換えない。略すと検索で見つからなくなり、窓口でも通じなくなる (「母子父子寡婦福祉資金貸付金」を「福祉のお金」にしない)
- **金額** — 丸めない (「48,050円」を「約5万円」に置き換えない。柔らかい言い方を添えるのは可: 「ざっくり月5万円くらい、正確には48,050円です」)
- **所得制限額・収入基準**
- **期限・申請期間・年度**
- **法令上の要件** (「18歳到達後最初の3月31日まで」→「18歳になった年の3月末まで」のような**同義の平易化は可**。要件そのものを落とすのは不可)

### ★危険語 = 平易にした結果、正確性を落とした表現 (★2026-07-26 追加・全記事必須★)★

上の「言い換え表」は**難しすぎる**のを直すためのもの。ここはその**逆方向の事故** ── 平易にしようとして事実を壊した ── を防ぐためのもの。**平易化ルールを入れたあと、実際に 2 回起きている**:

1. 児童扶養手当 (id=1) を「**毎月お金が入る**」と書いた → 実際は**奇数月・年6回**
2. 千葉県の医療費助成 (id=17) を「**自己負担300円まで**」と書いた → 実際は**市町村が定める1回あたりの負担額**で、総額の上限ではない

どちらも `article_md` 本体は正しく書けていた。**あとから `article_title` / `summary` だけを「読者の言葉」に書き直したときに**誤りが入っている。
**記事本体を直したあとにタイトル・summary を書き直すときも、同じファクトチェックを必ずやり直すこと。**

| 危険な表現 | なぜ危険か | 安全な言い換え |
|---|---|---|
| 毎月もらえる・毎月安くなる・毎月入る | 実際の振込頻度と食い違う | 月額で計算される／1か月あたりで算定される |
| 最大◯円もらえる | 全員がもらえるように読める | 条件を満たす場合の上限は◯円 |
| ◯円まで | 総額の上限に見える | 1回・1日など所定の単位で◯円 |
| 対象◯市 | 市の全域が対象に見える | ◯市内の対象区域 |
| 入学すれば返済不要 | 免除申請と認定が必要 | 入学後に免除申請をして認められた場合 |
| 当選確率が◯倍 | 実際の確率は応募状況で変わる | 抽せん番号が通常の◯倍割り当てられる |
| 申請期限は◯日 | 特別申請等の申請機会を見落とす | 通常の申請期限は◯日。ほかの申請機会の有無も確認 |
| 無料・全員・自動・誰でも | 例外や要件を落としている | (要件を添える) |

**★これは禁止リストではない★** — どれも**文脈によっては正しい**。本当に毎月振り込まれる制度も、本当に所得制限がない制度もある。
だから機械検出 (`M20` / `E24`) も CRIT ではなく **WARN**で、意味は「**本当に正しいか一次情報で確かめてから書け**」。
確かめた結果そのとおりなら、その表現のまま書いてよい。

**藤井先生の解説も対象**。「言い換え表」(役所語) は藤井を対象外にしているが、こちらは対象に含める。役所語は**読みやすさ**の話なので藤井は制度用語を使ってよいが、危険語は**正確さ**の話であり、**藤井の口から出た誤りこそ読者に最も信じられてしまう**。

> この表は `scripts/article_health_check.py` の `DANGER_PATTERNS` (`M20`) および
> `support-article-reviewer` skill の `DANGER_PATTERNS` (`E24`) と**同じ内容**。3 か所を同時に更新する。

### 言い換えると不正確になる語 = 「初出かっこ説明」方式

`所得` `控除` `扶養親族` `現況届` のように、平易な語に置き換えると意味が変わってしまう語は、**消さずに残し、初出時にかっこで説明を添える**:

- ✅ `所得（収入から必要な分を差し引いた額）から所得税は35万円を引きます`
- ✅ `毎年出す届出（現況届）を忘れると手当が止まります`
- ❌ `所得から35万円を控除できます` (説明なしで役所語を素通し)
- ❌ `もうけから35万円を引けます` (言い換えて不正確になった)

同じテキスト内で 2 回目以降はかっこ不要。`article_title` は字数の都合でかっこを置けないため、この方式の対象外。

### `summary` の書き方 (トップのカード説明文 = meta description)

読者が知りたい順に並べる: **①何がどうなるか → ②誰が → ③いくら／どのくらい**。

- 制度の**目的規定を写さない** (法第1条の書き写しは禁止)
- 「〜のために支給される手当」で始めない。「〜がもらえる制度」「〜が安くなる制度」で始める
- ★**振込頻度を書くなら、公式ページで実際の頻度を確認してから書く**★ (「危険語」の表を参照)。確認していないなら**頻度に触れず**「月額最大◯円」とだけ書く
- ★SEO: 「シングルマザー」を自然に含める★ (SEO 同義語ルールを維持)
- 目安 90〜200 字

例 (id=1 児童扶養手当):

> ❌ ひとり親家庭の生活の安定と自立の促進のために支給される手当。18歳到達後最初の3月31日までの児童 (障害がある場合は20歳未満) を養育する母・父・養育者が対象。
> (役所語・目的規定の写し。読者には何も伝わらない)
>
> ❌ シングルマザー・シングルファーザーの家庭に**毎月お金が入る**制度。子どもが18歳になった年の3月末まで（障害があるときは20歳未満まで）もらえます。第1子は月額最大48,050円で、収入によって全額もらえる人と一部だけの人がいます。
> (★これが 2026-07-26 の事故そのもの★。平易さは良いが、**児童扶養手当は奇数月・年6回払いで「毎月」は事実に反する**)
>
> ✅ 子どもが18歳に達した日以後の最初の3月31日まで（障害があるときは20歳未満まで）、生活費の手当がもらえる制度。シングルマザー・シングルファーザーの家庭が対象です。第1子は月額最大48,050円で、**支払いは奇数月に年6回、2か月分ずつまとめて振り込まれます**。収入によって全額もらえる人と一部だけの人がいます。

### 自己検出

DB 保存前に必ず実行する (プレデリバリー検証 第 1 段階の一部):

```bash
# M19 = 役所語 (article_title / summary / みさきの発言 / 見出し。藤井の発言は対象外)
# M20 = 危険語 (上記 + ★藤井の解説も対象★)
# M21 = 制度タイプ別の必須項目もれ / M22 = 記事末尾の構成順
bash scripts/article-health-check.sh --quick --id {id} 2>/dev/null | grep -E 'M19|M20|M21|M22' || echo 'M19-M22: 指摘なし'
```

- **M19** が 1 件でも出たら、言い換え表で直してから DB 保存する
- **M20** は禁止ではなく「本当に正しいか確かめよ」の合図。**一次情報で確認し、事実ならそのまま書いてよい**。事実でなければ「安全な言い換え」に直す
- **M21** が出たら、その論点を一次情報で調べて本文に書き足す
- **M22** が出たら、末尾の 4 セクションの順を直す

## 実行フロー

```
1. 対象の支援制度を特定
   - article_md IS NULL の制度
   - 1 回の実行で最大 3 記事

2. DB 内の制度データを取得
   $ bash scripts/supabase-query.sh select supports "id=eq.{id}&select=*"
   → title, summary, category, amount_max, amount_note, support_rate, source_url, official_url 等

3. Web 調査で追加調査 (research_notes に逐次記録) ※Claude Code 内蔵ツール・APIキー不要
   - 制度名で検索 → WebSearch("{制度名} ひとり親")
   - 公式ページ本文取得 → WebFetch(url="{official_url}", prompt="支給額・所得制限・対象者・申請方法・必要書類を抜き出す")
   - 競合分析: README.md「カスタマイズの指針」 を読み、記載の「執筆時の競合チェック手順」で SERP 上位 3 件と比較
   - ★年度改正チェック (必須)★: WebSearch("{制度名} 令和{当年度}年度 拡充 新設 改正") で当年度の新設制度・増額・期間延長を必ず確認する。見落とすと「最新年度」を掲げた記事に旧制度しか載らない事故になる (例: 令和8年度新設の高等職業訓練促進継続給付金)
   - ★税制記事の追加ルール★: ①所得税は「{X}年**分**」、住民税は「{X}年度**分**」と必ず区別し、「{X}年の所得 → {X+1}年度の住民税に反映」の対応関係を明示する ②財務省の「令和{当年度}年度税制改正大綱」を必ず確認し、控除額・所得要件の改正 (適用開始年分含む) を反映する (例: 令和8年度改正で扶養親族等の所得要件が58万→62万円)

4. 記事執筆 (下記フォーマットに厳密に従う)

5. ★ 図解画像生成 (最低 2 枚・独立ステップ・省略禁止) ★
   - Gemini 3.1 Flash Image Preview で生成
   - Supabase Storage `article-images` bucket にアップロード
   - 200 確認後にのみ DB 投入

6. ファクトチェック (4 段階・必須)

7. DB 保存 (article_md + article_title + research_notes を同時 UPDATE)
```

## research_notes 書き込み (★必須★)

**なぜ必要か**: レビュアー が引用した数字や固有名詞の一次ソースを照合するため。これがないと「どこから持ってきた情報か」が不明でファクトチェック不能 → **無条件で差し戻し**される。

### 収集タイミング (★調査フェーズで逐次記録、後から思い出さない★)

- 公式ページ・自治体公式 URL を開いたら即 `sources` に追記
- 金額・所得制限・支給月など数字や固有名詞を記事に書いたら即 `quotes` に追記 (`used_in` に記事中の使用箇所を残す)
- 競合記事を分析したら `competitor_analysis` に要約を記録

### 必須フィールド

- **sources**: 最低 3 件 (公式 URL 1 つ必須、3 件未満 = 調査不十分で差し戻し)
- **quotes**: 金額・所得制限・支給月・要件など具体的数字は必ず出典 quote 付き
- **reviewer_verifications**: **書かない** (レビュアーが追記するフィールド)

### 違反時の扱い

- research_notes が NULL のまま DB 保存 → レビュアーが**無条件で差し戻し**
- sources が 3 件未満 → **差し戻し** (調査不足)
- 数字を記事に書いたのに対応 quote がない → レビュアーが**該当箇所の削除指示**
- 公式 URL (.go.jp / pref.\*.jp / city.\*.jp 等) が sources に 1 つもない → **差し戻し**

## 対話形式記事の生成 (article_md)

### ★★★ 最初に読むもの: 登場人物と口調の設定ファイル ★★★

**執筆を始める前に、必ず `config/persona.json` を Read すること。**
（無ければ `config/persona.example.json` を読む。運用時は `cp config/persona.example.json config/persona.json` して自分のサイト用に編集する）

このファイルには**登場人物の名前・年齢・立場・一人称・口調・使ってよい語彙**が定義されている。
**記事内の名前・口調・例示は、すべてこのファイルの定義に従うこと。この SKILL に書かれた名前をハードコードしないこと。**

> なぜ外に出しているか: キャラクター設定は「そのサイトの事情」であって仕組みの本体ではない。
> 別テーマに移すときに設定ファイルだけ差し替えれば済むようにしてある。
> 一方、**役割の非対称性ルール（下記）と過去の事故の実例は、この SKILL 本体に残してある**。
> 題材が変わっても通用する普遍的なルールなので、設定に出すと意味が失われるため。

### 記事フォーマット

2 人の掛け合い形式で解説する。以下は `config/persona.example.json` の既定値の場合の例。

- **みさき** (`questioner` / 左側): **質問する側**。読者代理。素朴な疑問・実感・確認
- **藤井** (`explainer` / 右側): **回答・解説する側**。制度に詳しい専門家。具体的な数字・実務知見でやさしく解説

★人物の詳細（年齢・家族構成・収入帯など）は `config/persona.json` の `characters[].profile` が正本。
**記事内の例示・計算はこの設定と矛盾させないこと**（例: 質問役を例にするなら、そのプロフィールの子の人数・所得帯で計算する）。

> 質問役は読者代理だが、記事は**その属性の人だけに向けて書くのではない**。
> 対象を限定しない制度では、解説役のセリフで「お父さんの場合も同じです」等の補足を必ず入れる。

### ★★★ 話者の役割ルール (絶対厳守 / キャラを変えても引き継ぐ) ★★★

**このルールは登場人物が誰であっても変わらない。** `config/persona.json` の `id` で読むこと。

- **`questioner` = 質問役**: 「〜ですか？」「〜ってどういうことですか？」のように聞く側
- **`explainer` = 解説役**: 質問役の質問に対して具体的に答え、説明する側
- **逆転禁止**: 解説役が質問して質問役が解説するパターンは絶対 NG
- 記事は必ず**質問役の発言 (質問) から始める**こと
- DB 保存前に必ず全発言をチェックし、解説役の発言に「？」「ですか」が多い場合は役割が逆転している

> ★この非対称性が、このキットの品質の要です。★
> 質問役に専門用語を使わせないことで「読みやすさ」を、
> 解説役に正確性チェックを効かせることで「正確さ」を、それぞれ別の担当に持たせています。
> 1 人のキャラに両方を担当させると、どちらかが必ず崩れます。

### 吹き出しルール

- ★ 基本的に全テキストは吹き出し (`**みさき**:` or `**藤井**:`) 内で解説
- ★ 吹き出し外に置いていいのは: H2 見出し、テーブル、:::pointbox、:::warning、:::steps、画像のみ
- ★ 吹き出し内で番号リスト (1. 2. 3.) や箇条書き (- ) を使わない
- ★ `**太字**:` パターンは話者記法専用。他用途で使うと DialogueBubble 化される。見出しにしたい場合は `### 見出し` を使う

### 記法ルール

- 話者記法: `**藤井**: テキスト` / `**みさき**: テキスト`
- ★ コロンは必ず半角 `:`。全角 `：` は DialogueBubble に変換されない
- ★ H1 タイトル行 (`# ...`) は入れない (ページ側で article_title を表示)
- ★ 導入文 (「この記事では〜解説します」) は入れない (AI 臭い。いきなり対話から)
- ★ 水平線 `---` は使わない

### 時制ルール (鮮度劣化防止)

- 「もうすぐ」「今すぐ」「来月」「先月」等の相対時制は禁止。必ず絶対日付
- ❌「もうすぐじゃないですか！」→ ✅「7月11日が振込日なので、口座を確認しておきましょう」
- ❌「今年度から変更されました」→ ✅「令和8年度 (2026年度) から変更されました」
- ❌「最近の物価高」→ ✅「2025年以降の物価高騰」
- 記事は半年〜1 年後に読まれても違和感がないように
- 時刻表記: `HH:MM` 形式は禁止 (`:数字` が remark-directive に誤認)。`HH時MM分` で書く

### 金額表記ルール (★ひとり親支援固有・厳守★)

- 金額には必ず **月額 / 年額 / 一回限り** の別を明記する (「48,040円」単独は NG。「月額 48,040円」)
- 上限額・満額を見出しやタイトルに使うときは必ず「**最大**」を付ける (全員がもらえる額と誤読させない)
- **「最大」は加算・増額措置を含めた真の上限額を使う** (例: 高等職業訓練促進給付金は基本月10万円だが最終12か月は+4万円 → 「最大14万円」が正)。基本額を「最大」と書くのは誤り
- タイトルの金額が特定の世帯区分 (非課税世帯等) の額である場合、**タイトル直下に「※この金額は〜の場合です」の注記**を置く
- 年度で改定される金額 (手当・年金) は必ず**年度を併記**: 「月額 48,050円 (令和8年度)」
- 所得制限がある制度は**扶養人数別の目安**をテーブルで示し、境界の扱い (「未満」「以上」) を表の下に明記する
- 自治体差がある制度 (医療費助成等) は「全国共通の枠組み + お住まいの自治体で要確認」の構造で書き、特定自治体の数値を全国の数値のように書かない
- **「月額◯円」と書くときは、実際の支払い頻度 (年何回・何月) を必ずセットで確認し、混同しないこと**。「月額で計算される」ことと「実際に毎月振り込まれる」ことは別物。支払い頻度を確認せずに「月額」だけを見て「毎月もらえる」と書かない
- **タイトル・summary で「毎月もらえる」「毎月入る」と書いてよいのは、実際に毎月振り込まれる制度だけ**。年6回・偶数月・奇数月払いなど、月額計算でも振込が毎月でない制度では、頻度を確認したうえで「◯月ごとに」「年◯回」など実際の頻度で書く
  - **実例 (事故)**: 2026-07-26、児童扶養手当 (id=1) のタイトル・summaryを「読者の言葉」に書き換えた際、月額で決まる制度 (月額最大48,050円) を「毎月お金が入る」と誤って書いた。実際の支払いは奇数月に2か月分ずつ・年6回。児童手当 (id=2) でも同様に「高校生まで毎月もらえる」と誤って書いた (実際は偶数月・年6回)。article_md本体は正しく書けていたのに、後から書き換えたarticle_title/summaryだけがこの混同を持ち込んでいた。**article_mdを直した後にタイトル・summaryを書き直すときも、同じファクトチェックを必ずやり直すこと**

### 全国共通と自治体差の峻別ルール (★2026-07-22 外部レビューで追加・厳守★)

調査中に自治体サイト (city.\*.jp / pref.\*.jp) から取った情報は**その自治体のローカル運用かもしれない**と常に疑う。全国記事に書いてよいのは国 (cfa.go.jp 等) のソースで裏取りできた枠組みだけ。

- **振込日・支払日の具体日付は書かない** (支給月は全国共通でも日付は自治体ごと)。「具体的な振込日は市区町村によって異なります」と書く
- **必要書類は「一例」として書く**。表の前に「必要書類は、申請理由や世帯状況、市区町村によって異なります。以下は一例です。窓口へ行く前に、必ずお住まいの市区町村へ確認してください。」を必ず置く。年金手帳・健康保険証を全国必須のように書かない (従来型健康保険証は 2024-12-02 以降新規発行なし)
- **金融機関の可否 (「ゆうちょ不可」等) を断定しない**
- **「〜する自治体が増えています」等の傾向表現は統計的根拠がなければ書かない**
- ★**禁止語を並べるだけでは、語順を変えて再発する**★ (2026-07-27 実例)
  就学援助の記事で、初稿の「多くの自治体では」を7箇所直した直後に、
  **「対象になっている自治体が多い」**という形で同じ主張が復活し、機械チェックをすり抜けた。
  さらに **神戸市1件の締切しか根拠がないのに「締切が早いことが多い」を4箇所で反復**していた。
  → 覚えるべきは語のリストではなく **「いくつ調べたか」と「どう書いたか」を一致させる** こと。
    1自治体しか確認していないなら、書けるのは「**◯◯市では〜となっています**」まで。
    「多い」「一般的」「増えている」は、**国の統計など全国を見た資料がある場合だけ**使う。
- **「多くの自治体で」「ほとんどの自治体」「〜が一般的」も同罪** — 全国統計・国の公式資料で裏取りできない限り「〜する自治体があります」「自治体によって異なります」に言い換える。数自治体の例を調べただけで全国傾向を語らない
- 制度の資格判定 (事実婚・扶養義務者・施設入所等) は「自治体が生活実態等を踏まえて判断します」「〜となる場合があります」の形にし、単純化して断定しない
- **自治体実施型の事業 (都道府県・市・福祉事務所設置町村等が実施する給付金等) は「未実施の自治体では受給できない」ことを必ず明記**し、最初の行動を「居住自治体に実施状況と窓口を確認する」に置く
- **自治体差が本体の制度 (医療費助成・日常生活支援等) は「確認ポイント提示型」で書く**: 全国共通の制度解説の形を取らず、「①誰が対象か ②誰の分が助成されるか ③所得制限 ④窓口負担と償還払い ⑤申請期限・更新手続き」の確認ポイントを軸に構成し、自治体の具体数値は「参考例」として確認日付きで載せる
- **自治体の具体数値を並べる比較表**には直前に必ず注記: 「※以下は{確認年月}に各自治体の公式サイトで確認した制度例です。制度改正や市区町村独自の上乗せにより変更されることがあります。実際の利用前に、必ず居住自治体の最新情報をご確認ください。」

### 記事末尾の免責注意書き (★全記事必須★)

記事の最後 (FAQ_JSON コメントの前) に必ず以下を入れる (**時点は執筆日の年月**・制度名は記事に合わせる):

> ※本記事は令和{X}年{M}月時点の公表情報をもとに作成しています。{制度名}の認定、所得計算、必要書類、振込日などは、個別の状況や市区町村によって異なります。最新情報は、お住まいの市区町村の担当窓口でご確認ください。

### 対象者の断定禁止 (★2026-07-22 外部レビューで追加★)

- 「**すべての家庭/世帯が対象**」型の断定は書かない。所得制限がなくても居住・監護・生計同一などの支給要件は必ずある → 「原則として〜を満たす方が対象」の形で書く
- 「所得制限なし」は「所得の高さだけを理由に対象外となることはありません。ただし所得以外の支給要件はあります」の形に
- 他制度に言及するときも対象者を単純化断定しない (例: 児童扶養手当は「ひとり親専用」ではなく、父母の一方が一定の障害状態にある家庭や養育者も対象)

### 記事に含める情報

DB の制度データを全て対話形式に変換:

1. 導入・背景 (summary) — みさきの実感ベースの疑問から入る
2. 制度の概要 — 誰のための何の制度か、母子/父子両方対象かを明示
3. 支給額・給付額の詳細 (amount_max, amount_note, support_rate) — テーブル必須、月額/年額明記
4. 対象者・受給資格 — 所得制限・子どもの年齢要件を具体的に列挙
5. 必要書類 — 窓口に行く前に揃えるもの
6. 申請の流れ — :::steps 必須
7. 注意点 (現況届・併給調整・再婚等での資格喪失) — :::warning 必須
8. 基本情報まとめテーブル (支給額・所得制限・申請窓口・公式 URL)
9. 併用できる他の支援制度 — ★DB 内の実 ID で内部リンク必須★
10. よくある質問 — 対話形式 + `<!-- FAQ_JSON [...] -->` コメント
11. 関連書類・リンク (source_url, official_url)

### ★制度タイプ別の必須項目 (★2026-07-26 追加・全記事必須★)★

上の 1〜11 はどの制度にも共通の骨格。それに加えて、**`supports.category` から決まる制度タイプごとに「必ず確認して書く項目」**がある。**記事の構成を変える話ではなく、この論点に一度も触れずに公開しないためのチェックリスト**:

| `supports.category` | 制度タイプ | 必ず確認する項目 |
|---|---|---|
| `手当` / `給付金` / `年金` | **手当・給付** | 算定単位／実際の振込月／申請期限／遡及の可否 |
| `貸付` | **貸付** | 入金時期／審査／返済開始／返済期間／免除手続き |
| `助成` / `税制` | **医療・減免** | 対象外費用／負担額の単位／事前申請／区域差 |
| `サービス` | **サービス・住宅** | 実施地域／募集・予約時期／利用上限／利用できない場合 |

**なぜこの表が要るのか**: 「毎月お金が入る」(実際は奇数月・年6回)、「自己負担300円まで」(実際は1回あたりの額) の 2 つの事故は、どちらも**その型なら必ず書くはずの論点 ── 実際の振込月 / 負担額の単位 ── を書かないまま平易化した**ことで起きている。「危険語」の表が**書いてしまった誤り**を止めるのに対し、この表は**書かなかった穴**を塞ぐ。

- 各項目は**一次情報 (official_url) で確認してから**書く。調べて分からなかったものは「公式ページに記載がないため、窓口で確認してください」と正直に書く (推測で埋めない)
- 機械検出は `M21` (公開後) / `E23` (公開前)。キーワードの有無しか見ないので、**出なくても書けているとは限らない**
- 制度タイプ表を増やすときは `scripts/article_health_check.py` の `CATEGORY_TO_TYPE` / `TYPE_REQUIRED` と `support-article-reviewer` skill の同名の表も同時に更新する

### ★記事末尾の構成 (★2026-07-26 追加・全記事必須・順番厳守★)★

**なぜこのルールが要るのか**: 記事ごとに末尾の並びがバラバラだった。「参考リンク」がある記事とない記事があり、「基本情報まとめ」と「併用制度」の順番も一定しない。読者は複数の制度をはしごして読むので、**記事が変わるたびに情報の場所が変わると探し直しになる**。末尾は「読み終わったあとに動く」ための場所なので、ここだけは並びを固定する。

記事の末尾は、**必ず次の 4 つをこの順で**置く (H2 見出し):

```
## 基本情報まとめ            ← 1. 支給額・所得制限・申請窓口・公式 URL のテーブル
## 併用できる他の支援制度     ← 2. ★DB 内の実 ID で内部リンク必須★
## よくある質問              ← 3. 対話形式 + <!-- FAQ_JSON [...] --> コメント
## 公式情報・問い合わせ先     ← 4. official_url / source_url / 窓口 (:::pointbox{title="問い合わせ先"})
```

- **4 つとも省略しない**。「併用できる制度が思いつかない」場合でも、`target_scope` が近い制度を最低 1 つは探して内部リンクする
- **この 4 つの間に別の H2 を挟まない**。書きたい補足 (「◯◯との違い」「実は他にもこんな選択肢が」等) は**基本情報まとめより前**に置く
- **4 番目は H2 でも `:::pointbox{title="問い合わせ先"}` でもよい**が、どちらも無いのは NG。見出し名は「公式情報・問い合わせ先」「参考リンク」のどちらでもよい
- 免責注意書き (※本記事は…) と `<!-- FAQ_JSON ... -->` は**この 4 つより後**、記事の最後に置く
- 1 番目の見出しに制度名を入れるのは可 (「児童手当の基本情報まとめ」)。**順番さえ守れば見出し語の揺れは許容**する
- ★**既存記事をこの順に作り直す作業は別途**★。このルールは**今後書く記事**に適用する。機械検出は `scripts/article_health_check.py` の `M22` (INFO 固定)

### article_title のルール (★2026-07-26 に型を統一★)

**型**:

```
平易な一言 ｜ [地域の]制度名 は 数字・特徴 【年度】
```

例 (全て実在の記事):

| id | article_title |
|---|---|
| 1 | `毎月お金が入る｜児童扶養手当は月額最大48,050円【令和8年度】` |
| 4 | `資格をとる間の生活費｜高等職業訓練促進給付金は月額最大14万円【令和8年度】` |
| 6 | `借りて返すお金｜母子父子寡婦福祉資金貸付金は12種類【令和8年度】` |
| 9 | `税金が安くなる｜ひとり親控除は所得から最大35万円【2026年分】` |
| 13 | `当たりやすくなる｜東京都の都営住宅は優遇抽せん7倍【令和8年度】` |

ルール:

- **平易な一言**は、その制度で読者の生活が「どう変わるか」を**動詞**で言う。6〜12 字程度。「読者の言葉で書くルール」を適用する (役所語禁止)
- **地域名** (「東京都の」) は地域制度のみ。**制度名の直前**に置く
- **制度名は正式名称のまま**。略さない・言い換えない (検索されなくなり、窓口でも通じなくなる)
- **数字**があれば入れる (`amount_max` / 倍率 / 種類数)。無い制度は特徴 (「自治体ごとに違う」等)
- **【年度】は必ず末尾**。税制のみ【2026年分】のように「年分」
- 上限額を出すときは必ず「**最大**」を付ける (金額表記ルールと同じ)
- ★**全角 40 字前後に収める**★。超える場合は数字の後ろの要素を削るか、平易な一言を縮める。**必ず `len()` で実測すること** (目分量禁止)

```bash
python -c "t='毎月お金が入る｜児童扶養手当は月額最大48,050円【令和8年度】'; print(len(t))"
```

### トンマナ (絶対遵守)

- あたたかく、実用的に。読者を急かさない・不安を煽らない
- フィラー: 「えっ」「ほんとですか？」「なるほど」「それは助かります」
- みさきの短い実感リアクション (10-25 文字) を 4-7 交換ごとに挟む (例: 「それなら私も対象かも」)
- 1 バブル最大 6 文
- 数字は柔らかく言い換えつつ正確な値も併記: 「ざっくり月5万円くらい、正確には48,040円ですね」
- 禁止: 「〜することができます」「整理すると」「第一に」「したがって」
- KW はスペース区切りで直接入れない。自然な助詞でつなぐ

### 装飾ディレクティブ (全て使うこと)

- `<mark>重要テキスト</mark>` — 黄色マーカー。10 回以上
- `:::pointbox{title="..."}` — 赤ヘッダーのポイントボックス。2 回以上
- `:::warning{title="..."}` — 赤ヘッダーの警告ボックス。2 回以上
- `:::steps` — ステップバイステップ。1 回以上
- テーブル `| header | header |` — 3 つ以上
- ★ ディレクティブ記法は `:::warning{title="..."}` (中括弧必須)。`:::warning title="..."` は不可

> ディレクティブの実装は受け取り側の Next.js / remark プラグインに依存します。同等の実装が無い場合は、適宜 HTML や Markdown 標準記法に置き換えてください。

### ディレクティブ内・吹き出し内の絶対ルール

**1. URL を `<mark>` で囲まない**

- ❌ `<mark>今日中に公式ページ (https://www.city...)で申請書をダウンロード</mark>` → 黄色 + 自動リンク + 吹き出し背景の 3 重スタイル衝突で読めなくなる
- ✅ `<mark>今日中に[公式ページ](https://www.city...)で申請書をダウンロード</mark>` (mark の中に anchor text 形式で URL)
- ✅ `<mark>今日中に公式ページで申請書をダウンロード</mark>。詳細は[公式ページ](https://...)を参照。` (mark とリンクを分離)

**2. `:::pointbox` `:::warning` `:::steps` の中で `**xxx** ...` (bold + 半角空白) パターン禁止**

- ❌ `**手当①** 児童扶養手当は...` → フロントの話者バブル regex (`^\*\*[^*]+\*\*`) が話者と誤判定し、緑の吹き出し中に誤レンダリング
- ✅ `- **手当①**: 児童扶養手当は...` (リスト形式 + コロン)
- ✅ `**手当①：** 児童扶養手当は...` (コロン込みの bold)

**3. 長い URL は anchor text 形式で**

- ❌ `公式ページ (https://www.cfa.go.jp/policies/hitori-oya/fuyou-teate)`
- ✅ `[公式ページ](https://www.cfa.go.jp/policies/hitori-oya/fuyou-teate)`
- 例外: テーブルの「公式ページ | https://...」セルは生 URL OK (テーブル内は overflow-wrap で安全)

## 図解画像 (最低 2 枚・★保存先は Supabase Storage★)

> **Lite 版では、この節は `config/features.json` の `images` が `true` のときだけ行う。** 既定は `false` なので、画像は作らず次の節へ進む
> （画像を作るには Gemini の API キーと画像の置き場所が要る。足し方は `addons/README.md`）。

Gemini 3.1 Flash Image Preview で生成 → **Supabase Storage `article-images` bucket** にアップロードして使う。

```bash
source .env.local

# 1. Gemini で画像生成 (base64 で受信)
curl -s "https://generativelanguage.googleapis.com/v1beta/models/gemini-3.1-flash-image-preview:generateContent?key=${GEMINI_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"contents":[{"parts":[{"text":"プロンプト"}]}],"generationConfig":{"responseModalities":["TEXT","IMAGE"]}}' \
  | python3 -c "import sys,json,base64; d=json.load(sys.stdin); b=d['candidates'][0]['content']['parts'][1]['inlineData']['data']; open('/tmp/{id}-{name}.png','wb').write(base64.b64decode(b))"

# 2. Supabase Storage にアップロード (upsert=true で上書き可)
FILE="/tmp/{id}-{name}.png"
curl -s -X POST \
  "${NEXT_PUBLIC_SUPABASE_URL}/storage/v1/object/article-images/{id}-{name}.png" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Content-Type: image/png" \
  -H "x-upsert: true" \
  --data-binary "@$FILE"

# 3. 配信確認 (200 が返るまで記事投入しない)
IMG_URL="${NEXT_PUBLIC_SUPABASE_URL}/storage/v1/object/public/article-images/{id}-{name}.png"
code=$(curl -s -o /dev/null -w '%{http_code}' "$IMG_URL")
[ "$code" = "200" ] || { echo "FAIL: 画像配信 $code"; exit 1; }
```

- **記事中**: `![代替テキスト](${NEXT_PUBLIC_SUPABASE_URL}/storage/v1/object/public/article-images/{id}-{name}.png)`
- ★ 画像は H2 見出しの直後に配置 (吹き出し内に入れない)
- 白背景、フラットデザイン、テキスト全て日本語、アクセントカラー #FACC15
- 図解テーマの例: 支給額早見表、申請の流れ、所得制限のイメージ、併用できる制度マップ
- 日本語テキストはシンプルに (長い説明文は Gemini で崩れやすい)

### ★画像内テキストの事故防止ルール (必ず守る)★

過去に「児童扶養手当の支給額表なのに画像内タイトルが『令和8年度 認可保育園 保育料』」「児童育成手当の比較図がゴールドカードの比較広告」「都営住宅の図解が『黄色について #FACC15』という色見本」といった重大事故が発生した。alt テキストが正しくても画像内が全く別物になることがある。以下を必ず守ること。

1. **制度名をプロンプト内で繰り返し明示する**
   - 冒頭に「これは『{制度名}』の図解です」と書き、さらに「★最重要★ {制度名}の図解です。{混同しやすい他制度名}の図では絶対にありません」と念押しする
   - 混同されたくない語を名指しで禁止する (例:「画像内に『保育料』『保育園』という語を絶対に入れない」)

2. **画像内に入れる文字は、プロンプトで一字一句すべて指定する**
   - 「画像内に描く文字は次の N 個の文字列だけです。これ以外の文字は一切描かないでください」と列挙形式で書く
   - 数字は「勝手に変更しない (48,050 / 11,350 はそのまま)」と明記する
   - ★プロンプト内で `見出し = ○○` のようなラベル構文を使うと「見出し＝甲優遇」とラベルごと画像に描かれる事故が起きる。ラベルは使わず、文字列を列挙してレイアウトは別項で説明する★

3. **Gemini の日本語描画の典型的な崩れを、プロンプトで先回りして禁止する**
   - 丸数字を指示すると「マル1」「マル2」とカタカナで描かれる → 必ず `STEP1` `STEP2` 形式を指定する
   - 同じ文がアイコンの上と下に**二重に描かれる** → 「各カードに文字は N 個だけ。重複して描かない」と明記
   - 折り返し時に行末の文字が次行頭で**重複**する (「健康保 / 保険証」) → 説明文は短く1行に収め、「折り返しても文字列が1回だけ読めるように」と指示
   - アイコン内の看板・書類に**存在しない日本語**が描かれる (「政府所」「公共務所」「家族証」) → 「イラスト・アイコンの中に文字を描き込まない。看板・プレート・書類・画面に文字を書かない」と指示し、それでも直らなければ**背景や建物のないシンプルな線画アイコンに変更する**

4. **生成後に必ず Read ツールで目視確認する (省略禁止)**
   - HTTP 200 やファイルサイズだけでは何の検証にもならない
   - 確認項目: ①画像内タイトルがその記事の制度名と一致しているか ②金額・数値が記事本文と一致しているか ③日本語が破綻していないか ④制度と無関係なモチーフが入っていないか
   - 小さい文字は PIL で該当部分を切り出して拡大し確認する:
     ```bash
     python -c "from PIL import Image; im=Image.open('x.png'); w,h=im.size; im.crop((0,int(h*0.75),w,h)).resize((w*2,int(h*0.25)*2)).save('_zoom.png')"
     ```
   - 誤りがあれば**プロンプトを修正してから**再生成する (同じプロンプトで引き直しても同じ失敗を繰り返す)

5. **既存の図を一部だけ直すときは image-to-image を第一選択にする**
   - 既存画像を inlineData で渡し「**変更するのは○○の文言だけ。それ以外のアイコン・配色・レイアウトは完全に同じにする**」と限定する
   - 実績: 「母子父子寡婦福祉資金 → 母子父子寡婦福祉資金貸付金」の見出し1語の修正が1回目で成功し、12個のアイコン・配色・3カラム構成が完全再現された
   - ゼロから作り直すと、直したい箇所以外で新しい崩れが生まれる。**部分修正でテキストから作り直してはいけない**

6. **禁止語だけでなく「許容語の出現位置と回数」まで指定する**
   - 誤りを直す再生成では、プロンプト冒頭に「★特に重要な訂正点★」として**旧図の誤り語を名指しで禁止**する
   - そのうえで、残したい語について**どこに何回出すか**を指定する
   - 実績: 「『在学中』は絶対に使わない。『12か月』は下部の帯に1回だけ出す」と指定したことで、1回目で成功した
   - カード見出しは `STEP1 修業前` のように**1つの文字列に統合**すると、見出し語がアイコン下にも重複描画される事故が起きない

7. **図を直したら alt テキストも必ず直す**
   - 過去に、図を修正したのに alt に旧図の誤り (「在学中12か月の給付」) が残る事故が発生した
   - alt はスクリーンリーダーと検索エンジンが読む**本文の一部**。画像だけ直して終わりにしない

## AI 臭フレーズ禁止リスト

- 「幅広く」「包括的に」「網羅的に」

## セクションブリッジ (H2 間の自然な接続)

各 H2 セクションの**冒頭**と**末尾**で、前後のセクションとの接続を作る。ぶつ切りの記事にしない。

### 冒頭ブリッジ

各 H2 の最初の吹き出しで「このセクションで何を話すか」を 1 文で示す。

### 末尾ブリッジ

各 H2 の最後の吹き出しで、次のセクションへの自然な接続文を入れる。

良い例:
- 「**みさき**: 対象になる条件はわかりました。実際の手続きはどうすればいいんですか？」→ `## 申請の流れ`
- 「**みさき**: 金額はわかったんですけど、私の収入でも受け取れるんでしょうか？」→ `## 所得制限`
- 「**藤井**: 申請の話が出たので、次は必要な書類を見ていきましょう」→ `## 必要書類`

## プレデリバリー検証 3 段階 (DB 保存前〜保存後)

Writer 自身が DB 保存前後に実施する検証。**全段階パスしないとレビュー依頼を出さない**。

### 第 1 段階: フォーマットチェック (DB 保存前)

article_md を以下の観点で機械的にチェック:

- AI 臭フレーズ禁止リストに該当する表現がないか (grep で検出)
- `**太字**:` パターンが話者 (みさき/藤井) 以外で使われてないか
- `<mark>` タグが 1 行内で閉じているか
- :::ディレクティブの開きと閉じの数が一致しているか
- H1 (`# ...`) が含まれてないか
- 時刻表記が `HH:MM` 形式になってないか (`HH時MM分` であること)
- 金額に月額/年額/一回限りの別が明記されているか
- セクションブリッジ: 各 H2 の冒頭と末尾に接続文があるか
- **図解画像が 2 枚以上埋め込まれているか**: `grep -cE '!\[[^]]*\]\(https://[^)]*article-images/' <<< "$article_md"` が 2 以上。不足なら DB 投入不可
- **埋め込んだ画像が Supabase に実在するか**: 各画像 URL に対して `curl -s -o /dev/null -w '%{http_code}'` が全て 200。404 があれば DB 投入不可
- **記事中の金額・率・件数すべてに対応する quote が research_notes.sources[*].quotes に存在するか** (quote 無しの数字は削除)
- **役所語が残っていないか (「読者の言葉で書くルール」)**: `bash scripts/article-health-check.sh --quick --id {id} | grep M19` が 0 件。対象は `article_title` / `summary` / みさきの発言 / 見出し (★藤井の解説は対象外★)
- **危険語が残っていないか (「危険語」の表)**: 同コマンドの `grep M20`。★禁止ではない★ ので 0 件である必要はないが、**出た 1 件ずつについて一次情報で確認済みであること**。特に `article_title` / `summary` を後から書き直した場合は必ず再確認する (★2 回の事故はどちらもここ★)
- **制度タイプ別の必須項目に全部触れているか**: 同コマンドの `grep M21` が 0 件 (出た場合は本文を読み、本当に欠けていれば書き足す)
- **記事末尾が 基本情報まとめ → 併用できる制度 → よくある質問 → 公式情報・問い合わせ先 の順か**: 同コマンドの `grep M22` が 0 件
- **`article_title` が新しい型 (`平易な一言｜[地域の]制度名は数字【年度】`) で、全角 40 字前後か** — `len()` で実測する

### 第 2 段階: ファクトチェック結果の確認 (DB 保存前)

上記 4 段階ファクトチェックの全項目がパスしていることを確認する。
1 件でも NG が残っていれば DB 保存しない。

### 第 3 段階: レンダリングチェック (DB 保存後)

article_md を DB に保存した後、**curl ベースのコンテンツ検証** を実施する。

```bash
source .env.local
ID={id}

# 1. HTTP 200 確認
code=$(curl -s -o /tmp/page-$ID.html -w '%{http_code}' "${PUBLIC_SITE_URL}/support/$ID")
[ "$code" = "200" ] || { echo "FAIL: HTTP $code"; exit 1; }

# 2. 画像 URL の 200 チェック
for url in $(grep -oE 'https://[^)"]*article-images/[^)"]+' /tmp/page-$ID.html); do
  img_code=$(curl -s -o /dev/null -w '%{http_code}' "$url")
  [ "$img_code" = "200" ] || { echo "FAIL: 画像 $img_code → $url"; exit 1; }
done

# 3. コンテンツ grep (受け取り側の Next.js DialogueBubble 実装に依存)
HTML=/tmp/page-$ID.html
grep -q 'dialogue-bubble-left' $HTML || { echo "FAIL: 左バブル無"; exit 1; }
grep -q 'dialogue-bubble-right' $HTML || { echo "FAIL: 右バブル無"; exit 1; }

img_count=$(grep -oE '<img[^>]*article-images[^>]*>' $HTML | wc -l | tr -d ' ')
[ "$img_count" -ge 2 ] || { echo "FAIL: 画像が $img_count 枚 < 2"; exit 1; }

! grep -qE ':::(warning|pointbox|steps)' $HTML || { echo "FAIL: 未変換ディレクティブあり"; exit 1; }

rm -f $HTML
echo "OK: 全 curl チェック合格"
```

手順:
1. 上記スクリプトで自動検証
2. 1 つでも FAIL なら問題を特定 → article_md を修正 → DB 再保存 → 再度 curl チェック → 全 OK まで繰り返す (最大 3 回)
3. 3 回修正しても直らない場合は article_md を NULL に戻す
4. 全 OK になって初めてレビュー依頼を出す
5. ※ フロントエンドサイト (PUBLIC_SITE_URL) が未構築・未起動の場合は本段階をスキップ可 (第 1・2 段階は必須)

★ チェックせずにレビュー依頼を出すのは絶対禁止 ★

## DB 保存

```bash
# 本文は /tmp/article_md_{id}.txt、調査メモは /tmp/research_notes_{id}.json に書いておき、ファイルごと渡す
# (Lite 版は jq を使わない。巨大な本文を引数に直接書くと argv 上限で失敗するので、必ずファイルで渡す)
bash scripts/supabase-query.sh set supports "id=eq.{id}" \
  article_md=@text:/tmp/article_md_{id}.txt \
  article_title="{記事タイトル}" \
  research_notes=@json:/tmp/research_notes_{id}.json
```

※ research_notes を書かないとレビュアーが無条件で差し戻す。

## 仕様追記時のメタルール (孤立ルール防止・絶対遵守)

このスキルに新しい品質要件 (「○○を必ずやる」等) を追加するときは、**以下の 3 レイヤー全てに同時に反映**すること。1 つでも漏れると「仕様書には書いてあるが実行時に守られない孤立ルール」になる。

1. **実行フロー**: 番号付きステップとして独立配置するか、既存ステップに明記
2. **プレデリバリー検証 第 1 段階**: grep/regex で機械検出できる形に落とす
3. **レンダリングチェック**: ブラウザ目視項目に追加

さらにレビュー側にも対応基準が必要なら、**`support-article-reviewer` skill にも同期**:

4. レビュアーのチェックリスト (A〜E のどれか)
5. レビュアーのフォーマットチェックスクリプト (Python 関数 `check_article` に検出コード追加)

そのルールが**公開後にも破れうる**もの (年度で腐る / 修正時に混入する / 図と本文がずれる) なら、さらに:

6. `support-article-maintenance` skill の検出コード表 + `scripts/article_health_check.py` に `Mxx` を追加

### 語彙表の同期 (★言い換え表を触るときは 3 か所同時★)

「読者の言葉で書くルール」の言い換え表は、**同じ語彙が 3 か所にコピーされている**。1 か所だけ足すと機械ゲートと仕様がずれる:

1. 本 skill の「言い換え表」 (定義元・人間が読む)
2. `support-article-reviewer` skill の `check_article` 内 `BUREAU_TERMS` (公開前ゲート `E20`)
3. `scripts/article_health_check.py` の `BUREAU_TERMS` (公開後ゲート `M19`)

**「危険語」の表も同じく 3 か所**にコピーされている:

1. 本 skill の「危険語」の表 (定義元)
2. `support-article-reviewer` skill の `DANGER_PATTERNS` (公開前ゲート `E24`)
3. `scripts/article_health_check.py` の `DANGER_PATTERNS` (公開後ゲート `M20`)

危険語を足すときは、**「同じ文にこれがあれば参考扱いにする文脈」もセットで書く**こと。これが無いと「毎月」「無料」のような**正しい使い方のほうが多い語**で警告が溢れ、本当に危ない 1 件が埋もれる。

語を足したら `bash scripts/article-health-check.sh --quick` を実行し、既存記事で誤検出が増えていないか確認する。制度の正式名称の一部に当たってしまう語は `BUREAU_TERM_RE` に否定先読みを足して逃がす (例: `養育(?!費)`)。

**How to apply**: 新ルールを書き終えたら自己問診:
- □ 実行フローの何番目で発動する？
- □ grep/regex で違反を検出できるか？
- □ レンダリングチェックに目視項目を追加したか？
- □ レビュアー側 (`support-article-reviewer` skill) に同期が必要か？ 必要なら両方更新したか？
- □ 公開後にも破れうるルールか？ Yes なら `support-article-maintenance` skill に `Mxx` を同期したか？

即答できなければルール未完成として書き直す。

## カスタマイズの指針

- **対話キャラ**: ★`config/persona.json` を書き換えるだけ★ (名前・年齢・口調・一人称・語彙)。
  ただし話者記法そのもの (`**名前**:`) を変える場合は、reviewer skill の `check_article()` の正規表現も直すこと
- **DB スキーマ**: `supports.summary` などのカラム名は `supabase/schema.sql` に揃える
- **画像生成**: Gemini 3.1 Flash Image Preview。他の画像生成 API (DALL-E / Imagen) に置き換える場合はこのセクションを書き換え
- **一次調査**: Claude Code 内蔵の WebFetch / WebSearch を使用 (APIキー不要)。手動 URL 指定でも可
- **公式ドメイン**: 公式 URL 判定は `.go.jp / pref.*.jp / city.*.jp` が日本前提。他国対応時は調整
