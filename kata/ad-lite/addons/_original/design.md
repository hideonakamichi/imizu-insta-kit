## スコープ

第一弾は **Metaに絞る**。Google・Yahoo!・LINEは次回以降。
入力：商品・サービス情報＋業種キーワード
出力：競合と被らないコンセプトのバナー画像群＋LP

## パイプライン（4ステージ＋公開）

```
[ 1. Scrape ] → [ 2. Analyze ] → [ 3. Banner ] → [ 4. LP ] → [ 5. Publish ]（任意）
```

| # | ステージ | 入力 | 出力 | 主な技術 | 担当エージェント |
|---|---|---|---|---|---|
| 1 | Scrape | キーワード | 競合広告の body_text（コピー） | Playwright で Meta広告ライブラリをスクレイプ＋XHRインターセプト | `ad-scraper` |
| 2 | Analyze | body_text 群 | 競合コンセプトマップ＋空きポジ座標 | Gemini Embedding→PCA→グリッド距離法 | `gap-analyst` |
| 3 | Banner | 空きポジのコンセプト記述 | バナー画像 | GPT-image-2 | `banner-designer` |
| 4 | LP | バナーのコンセプト＋商品情報 | HTML/Markdown のLP＋画像 | Claude本体＋GPT-image-2 | `lp-designer` |
| 5 | Publish | _sections.json＋セクション画像 | 静的LPサイト＋公開URL | 静的HTML組み立て＋Vercel CLI | `lp-publisher` |

### 設計方針：Publish は「画像積みLP」で公開する

lp-designer のセクション画像は日本語コピーを画像内に焼き込む設計のため、公開形態は
**最新セクション画像を縦に積んだ静的HTML**（日本の広告LPの標準形）とする。これにより:

- LP本文Markdownの構造に依存せず、ビルドが決定的（壊れない）
- 追従CTAボタンだけをHTML側で持ち、リンク先（LINE登録・フォーム等）は `--cta-url` で差し替え可能
- デプロイは Vercel CLI（プロジェクト名は lp_id から自動生成）。検証用途のため `noindex` を付与

公開は外部公開になるため、orchestrator は**ユーザーが求めたときだけ** lp-publisher を起動し、
本番（--prod）前にプレビューURLの確認を必ず挟む。

### 設計方針：空きポジ探索は「コピー」で測る

**画像分類（Filter）ステージは廃止**。理由：

- 空きポジ＝**訴求コンセプトの隙間**。これはコピーで決まる
- 症例写真ベースの広告でも、訴求軸（「ダウンタイム短縮」「価格訴求」など）は再利用可能なので除外不要
- 画像は最終の Banner ステージで「絵づくりの参考」に使う（必要なら）

このため scrape.py は既定で画像をダウンロードしない。`--with-images` で取得可。

## なぜオーケストレーター型に分けたのか（このフォルダの核）

前身の `meta-creative-pipeline` は「サブエージェントは増やしすぎず統合する」方針で、**1エージェントが
全4ステージ**を担い、**1スキルが全コマンド**を内包するモノリシック構成だった。動作はするが、

- 1エージェントに Scrape/Analyze/Banner/LP の4役割が集中し、コンテキストが混ざる
- スキルが肥大化し、各ステージの責務境界が曖昧

このフォルダは Claude Code のベストプラクティス（**サブエージェントは単一責任。主目的はコンテキスト分離**）
に沿って再設計した:

- **1エージェント = 1役割**。4ステージをそれぞれ専門サブエージェントに割り当てる。
- **`orchestrator` という統括役**を1本立て、各専門エージェントを `Agent` tool で起動・委譲する
  （フォアグラウンドのサブエージェント起動はネスト可能）。orchestrator 自身は実行せず、判断・制御に専念する。
- **スキルもステージごとに4分割**し、各スキルが自分の `scripts/` を同梱する（自己完結スキル）。

### この分割で得られるもの

- 各専門エージェントのコンテキストは自分のステージに閉じる（混線しない）
- 責務境界が明確（「これは誰の仕事か」が一意）
- スキルが小さく保たれ、トリガー精度（description）も鋭くなる
- 各スクリプトはスキル内に同梱され、スキル単位で持ち運べる

### トレードオフ

- エージェント／スキルのファイル数が増える（6エージェント＋5スキル）
- ステージ間の受け渡し（特に Analyze の訴求言語化 → Banner）は orchestrator が仲介する必要がある
  → orchestrator.md に受け渡し責務を明記してある

## エージェント構成

| エージェント | 役割（1つだけ） | 紐付くスキル |
|---|---|---|
| `orchestrator` | 全体の判断・制御・各専門エージェントの起動（実行はしない） | （なし） |
| `ad-scraper` | 競合広告コピーの収集 | scrape-toolkit |
| `gap-analyst` | 空きポジ分析＋「無い訴求」の言語化 | analyze-toolkit |
| `banner-designer` | バナー画像生成 | banner-toolkit |
| `lp-designer` | LP本文執筆＋セクション画像生成 | lp-toolkit |
| `lp-publisher` | LP静的サイト化＋Vercelデプロイ（公開URL発行） | publish-toolkit |

## スキル構成

| スキル | 内容 | 同梱スクリプト |
|---|---|---|
| `scrape-toolkit` | Meta広告ライブラリのスクレイプ手順 | scripts/scrape.py |
| `analyze-toolkit` | Embedding→PCA→空きポジ抽出の手順 | scripts/analyze.py |
| `banner-toolkit` | バナー生成（試打→目視→全生成）の手順 | scripts/banner.py |
| `lp-toolkit` | LP本文・セクション画像生成の手順 | scripts/lp_image.py |
| `publish-toolkit` | LP静的サイト化＋Vercelデプロイの手順 | scripts/publish.py |

## 検討中・未確定

- **空きポジションの判定アルゴリズム**：現状はPCA2D+グリッド距離法でTop-K。N=100以上の母数で精度検証必要。
  クラスタ密度の谷狙い（DBSCAN等）への切り替えも検討
- **Banner生成のプロンプト設計**：空きポジ近傍の競合コピーを gap-analyst が読んで「無い訴求」を言語化 →
  そのコンセプトを GPT-image-2 用プロンプトに整形する処理（現状は `banner.py` の `BRIEF` に手書き）
- **LPの出力形式**：HTMLベタ書きか、Astro/Next.jsテンプレ流し込みか。MVPは静的HTMLを想定
