# Writing Proposals

**提出の2ルール（最優先）** → [references/submission-rules.md](references/submission-rules.md)

| ルール | 要点 |
|--------|------|
| **① 一発出し** | スキル出力をそのまま提出物に。文章をチャットで何度も磨かない |
| **② 手作業修正禁止** | Typing で直さない。直すなら4問の材料を直して **最初から再実行** |

材料を集めるやり取りは **初めの4問だけ**（ルール①の対象外）。4問のあとは **提出用完成稿を1本だけ** 出す。

### 但し書き — 長い提案は章ごとに出す

完成稿が **1500文字を超えそうなとき** は、一発出しをやめて **章ごとに分割** する。1章を出して確認 → OK が出たら **その章を読み直してから** 次章、を最後まで繰り返す。前章を読み直すのが要で、章をまたぐ論旨と用語のずれをここで止める。

分割しても **ルール②（手作業修正禁止）は生きる。** 直すのは章の文ではなく4問の材料で、直したらその章から再実行する。

1500文字以内なら **従来どおり一発出し。** 提案は「結論 → 根拠 → 実施案」が一続きで成り立つため、この長さでは切らずに一息で書くほうが通る文章になる（一般の長文の基準は500文字。提案文だけ上限が高いのはこの理由）。

## クイックスタート（ユーザー向け）

- **起動:** 「**提案** で ◯◯」「提案文を作って」
- **流れ:** **初めの4問**（足りない分だけ）→ **提出用完成稿を1本**（一発出し）→ **そのまま提出**
- **直すとき:** 文を手で直さない → 4問の答えを整理 → **最初から再実行**
- **プレゼン:** 完成稿のあと a/b/c（下記 Step 5）

## 初めに聞く4問（これだけ）

起動時、ユーザーが **すでに言っていた項目は再質問しない**。未回答だけ **1問ずつ**（AskQuestion 推奨・推奨案つき）。**この4問以外は原則聞かない。**

| # | 聞くこと | メモ例 |
|---|----------|--------|
| **1** | **提案したい内容** | 何を変えたいか・テーマ |
| **2** | **誰に出すか** | 具体名 ＋ 対象タイプ A〜D（[audience-types.md](references/audience-types.md)） |
| **3** | **何を知りたいか** | 相手の頭の中の問い（No になる不安が分かればここに含める） |
| **4** | **何を言い切るか** | お願い・提案内容まで踏み込んだ結論 |

4問が揃ったら **追加の材料質問（根拠・心の話・AI方針など）はしない。** 答えに含まれる数字・事実・感情だけを使う。足りなければ一発出し内で控えめに書くか、一般論に逃げない（創作禁止）。

### ② 誰に出すか — 対象タイプ（4問の一部）

「誰に」の回答に **A〜D** を含める。ユーザーが「部長に」「取引先に」と言っていれば対応する ID をメモ。

| ID | 意味 |
|----|------|
| **A** | 直属上長・部長（社内承認・**推奨**） |
| **B** | 他部署・経営会議 |
| **C** | 顧客・取引先（社外） |
| **D** | 同僚・チーム内（合意形成） |

`対象: A — 部長` のように1行メモ。出力トーン・必須項目 → [audience-types.md](references/audience-types.md)

## 対話の進め方

1. **受け取る:** 起動文から4問を仮置きする
2. **4問を埋める:** 未回答だけ1問ずつ。**4問以外は聞かない**
3. **内部ゲート（ユーザーに下書きを見せない）:** [output-quality.md](references/output-quality.md) と [audience-types.md](references/audience-types.md) を満たせるか確認。4問が空なら **一発出しも出さない**
4. **一発出し（提出用完成稿）:** [examples.md](references/examples.md) で該当模範を1本読み、**完成稿をコードブロック1本だけ** 出力（`**` 禁止・装飾なし）。**【下書き】は出さない**  
   → **1500文字を超えそうなら章ごとに分割**（上記の但し書き）。各章もコードブロック1本・装飾なしは同じ
5. **プレゼン確認（任意）:** a/b/c（AskQuestion 推奨）  
   - **a. プレゼン原稿を作る** → `writing-presentations`（読み上げ原稿）  
   - **b. 提案書だけで終える**  
   - **c. プレゼン資料を作る** — `writing-slide-decks`（B 要否確認 → grill-me → （推奨）presentations → judge-panel → **スライド設計 A**・スタバトンマナ）。HTML 図解（B）は毎回確認・**デフォルト不要**

```
起動 → 4問（足りない分）→ 内部ゲート → 提出用完成稿1本 → そのまま提出
                              ↑
                    ユーザーには完成稿だけ見える
```

### 質問の例（4問の②③）

> ユーザー：提案で定例会議を減らしたい  
> AI（②）：誰に出しますか？ 社内なら直属上長（A）が自然です。  
> AI（③）：相手が知りたいのは「何がよくなるか／自分は何をすればいいか」で合っていますか？  
> AI（④）：何を言い切りますか？ 例：「週次定例を廃止し、非同期共有に切り替えてほしい」  
> AI：【提出用完成稿を1本出力】

## 文章を考える5ステップ（AI が一発出しで意識）

| # | ステップ | このスキルでの位置 |
|---|----------|-------------------|
| 1 | 誰に出すか | 4問② ＋ 対象 A〜D |
| 2 | 何を知りたがっているか | 4問③ |
| 3 | 何を言い切るか | 4問④ ＋ 4問① |
| 4 | 一発出し | examples 参照 → 完成稿1本 |
| 5 | 提出 | ルール② — 手直しせずそのまま |

## 心を動かす話・根拠・AI方針

- **別途質問しない。** 4問の答えに含まれる事実・数字・感情 **だけ** 使う（創作・誇張禁止）
- 4問に無い体験談は書かない
- 機能・自動化提案で AI 方針が4問に無い場合、本文に書かず省略（再実行時に4問へ追記）

## 基本ルール（執筆）

- **「が」でつなげない。** 列挙前に項目数を示す
- **結論＝要約＋判断** → [writing-basics.md](references/writing-basics.md)
- **メンツを守る言い換え** → 同ファイル

## 出力フォーマット

```
【提案】<[やること] ＋ [なぜ（4問にあれば）] ＋ [何をしてほしいか] を1行で言い切る>

◎ 現状の課題    … 事実（4問の数字・場面）
◎ 提案する理由   … 論理（4問にあれば心を動かす話を1〜2文）
◎ 選択肢と推奨   … 比較がある場合
◎ リスクと対策   … 4問③の不安への先回り
```

対象別の必須項目 → [audience-types.md](references/audience-types.md)（A: 工数・測り方等 / C: 相手メリット・次アクション 等）

## 提案 → プレゼン／資料連携

```
writing-proposals（4問 → 一発出し）
        ↓ Step 5
   a. presentations（原稿） ／  b. 終了 ／  c. slide-decks（資料 A）
        ↓ c で B=要 のときのみ
   creating-visual-explainers（HTML図解）
```

- **提案文は一発出しのまま提出。** 資料ルートの grill／ジャッジは **提案段落のチャット修正ではない**（深堀と品質ゲート）
- 資料パイプライン詳細 → `writing-slide-decks/references/material-pipeline.md`
- 元原稿: **一発出しの提案完成稿**

## 品質チェック

一発出しの直前に AI が内部適用 → [output-quality.md](references/output-quality.md)。ユーザー向けの下書き・グリル・ジャッジループは **行わない**。

**次にできること:** 完成稿をそのまま提出する。直すなら4問を直して最初から再実行する。発表が必要なら a / b / c。
