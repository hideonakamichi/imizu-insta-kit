# 出力品質チェックリスト

提案文書を出力する前に、以下を満たすか確認する。満たさない項目があれば直してから出力する。

**このファイルの役割:** 一発出し（[SKILL.md](../SKILL.md) Step 4）の直前に AI が内部適用。ユーザーに下書きは見せない。

**提出ルール:** [submission-rules.md](submission-rules.md) — 完成稿1本をそのまま提出。手作業修正禁止。

## 対象（4問②）

- [ ] `対象: A/B/C/D` が確定している（[audience-types.md](audience-types.md)）
- [ ] 対象 ID に合ったお願いの言い方になっている（A/B: 承認・判断依頼 / C: 検討・提案 / D: 合意・試行）
- [ ] 対象別の必須項目を満たしている（A: 工数・測り方等 / B: 他部署影響・スコープ / C: 相手メリット・次アクション・社内承認語なし / D: 役割分担・試験期間）

## 結論と構造

- [ ] 1行目が結論（＝相手へのお願い）になっている。要約で終わらず「だから何をしてほしいか」まで言い切っている
- [ ] 全体像 → 詳細の順になっている
- [ ] 事実・解釈・提案が混ざらず分かれている
- [ ] 心を動かす話は**ユーザーが提供した内容のみ**で、◎理由または◎課題に**自然な1〜2文**として入っている（AI の創作・誇張なし）。ユーザーが「特にない」と答えた場合は無くてよい
- [ ] 情報が階層構造（◎ → ・）で整理され、同じ階層に同じ粒度の情報だけが入っている
- [ ] 選択肢を示す場合、主要な案を網羅したうえで推奨案を明示している
- [ ] 工数・コスト・時間の削減を根拠にする場合、浮いたリソースの充当先まで書かれている
- [ ] 相手が断りそうな不安への対策（◎リスクと対策など）が本文にある
- [ ] 費用・ツール導入・有料の仕組みの場合、開始時期・期間総額（または合計が見える費用）・効果の測り方が本文にある

## 簡潔さと明確さ

- [ ] 「〜について」「〜の件」で逃げず、具体的なお願いになっている
- [ ] 一文が長すぎない（目安：30字以内、一文一義）。ただし削りすぎて意味が抜けていない
- [ ] 「品質」「早急に」など解釈の分かれる言葉に具体的な定義がある
- [ ] 同じ意味の言葉の表記揺れがない（用語が一貫している）
- [ ] 過剰な敬語で冗長になっていない
- [ ] 重要な数値や根拠が本文に書かれている（リンク頼みにしない）

## 仕上げ

- [ ] 箇条書きはMECE（漏れなく重複なく）で、語尾が統一されている
- [ ] 期限があるなら日時まで具体的（例：2026/07/01 17:00）。「予定」ではなく確定表現になっている
- [ ] 要点が1つだけの短い内容を、無理に階層化していない
- [ ] 意味の区切りで改行され、視覚的に読みやすい
- [ ] 番号付きリストは順序や手順がある場合のみ使っている（順番に意味がないときは「・」を使う）
- [ ] 箇条書きの下位項目が1つだけの場合は、箇条書き記号を使わず上位階層に含めている
- [ ] 同種の情報を並べるとき、列挙の前に「○つあります」と項目数を伝えている
